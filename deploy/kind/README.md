# Локальный Kubernetes через kind

[К оглавлению](../../docs/README.md)

kind запускает учебный Kubernetes внутри Docker на вашем компьютере. Он нужен, чтобы посмотреть, как то же приложение разворачивается через Helm, как работают отдельные миграционные Jobs и как Kubernetes следит за приложениями. Для первого запуска самого магазина проще использовать [Compose](../../README.md).

Здесь запускаются шесть Go-сервисов и отдельные PostgreSQL, Kafka, RustFS (S3) и Mailpit. Зависимости имеют по одной реплике: этот стенд не проверяет высокую доступность или работу после потери узла.

## Подготовка

Все команды ниже выполняйте **из корня репозитория**, не из папки `deploy/kind`. Нужны:

- работающий Docker Engine **28+**, API **1.48+**: скрипт использует `docker image save --platform`;
- Go, Make, Python 3 и установленный `kubectl`;
- сеть для загрузки инструментов/образов и свободные порты `18080`, `19000`, `18025`;
- достаточно памяти и диска для дополнительного Kubernetes-узла.

Compose и kind могут работать одновременно, но это **две независимые копии данных** с дополнительным расходом ресурсов. Если ресурсов мало, остановите Compose через `make down`: его постоянные тома сохранятся.

Проверить наличие инструментов без изменения стенда:

```sh
docker version
go version
python3 --version
kubectl version --client
```

В `docker version` должны быть доступны и Client, и Server. Если сервер недоступен, сначала запустите Docker. Если `kubectl` не найден, установите его до продолжения: `make tools` его не устанавливает.

## Запуск по шагам

```sh
make setup
make tools
make kind-up
```

1. `make setup` создаёт локальные секреты в `.local/.env`, если файла ещё нет. Существующие пароли не меняются.
2. `make tools` скачивает Helm и kind с проверкой контрольных сумм и устанавливает kubeconform. Инструменты находятся в `.local/bin`; системные установки не заменяются.
3. `make kind-up` сначала собирает образы приложения, затем выполняет [kind-up.sh](../../scripts/kind-up.sh). Внутренний вызов setup в скрипте не заменяет первый шаг: сборка образов Makefile происходит раньше него и уже нуждается в `.local/.env`.

Скрипт использует кластер **`marketplace-example`**, отдельный файл **`.local/kubeconfig`** и context **`kind-marketplace-example`**. Развёртывание не берёт ваш произвольный текущий context. Если кластер с этим именем уже есть, он используется повторно.

Что должно последовательно произойти:

1. Создание кластера, если он отсутствует, и namespace `marketplace`.
2. Импорт образов для архитектуры узла. Образы приложений имеют локальный тег `:dev`.
3. Создание Secrets из `.local/.env` и конфигурации инициализации PostgreSQL. Промежуточные секреты находятся в `.local/kind-secrets`; их тоже нельзя публиковать.
4. Запуск PostgreSQL, Kafka, S3 и Mailpit; ожидание завершения `kafka-init`.
5. Создание пяти Jobs миграции — по одной для каждой базы. При их ошибке приложение не обновляется следующим шагом.
6. Установка/обновление Helm release `marketplace`, затем перезапуск приложений, чтобы они использовали загруженные образы `:dev`.

Успешный конец — строка `kind ready: http://127.0.0.1:18080`. Первый запуск может долго скачивать образы. Если команда завершилась ошибкой, сначала изучите конкретный шаг и состояние ниже; удалять кластер для каждого сбоя не нужно.

## Открыть приложение и добавить данные

| Что | Адрес |
|---|---|
| Приложение | [127.0.0.1:18080](http://127.0.0.1:18080) |
| Учебная почта Mailpit | [127.0.0.1:18025](http://127.0.0.1:18025) |
| S3 API для фотографий | [127.0.0.1:19000](http://127.0.0.1:19000) |

S3 API — адрес для объектов и подписанных ссылок, не страница управления файлами. Порты соединяются с NodePort-сервисами внутри kind; вручную запускать `port-forward` для обычного сценария не нужно.

Демоданные загружаются отдельно:

```sh
go run ./cmd/seed --base-url http://127.0.0.1:18080
```

Ожидается сообщение `Demo users and listings ready`. Логины: `anna@example.com` и `boris@example.com`; пароль — значение `DEMO_PASSWORD` из локального `.env`. Команда использует именно kind-адрес. Обычный `make seed` по умолчанию обращается к Compose на `8080`.

Проверить сквозной сценарий:

```sh
make kind-smoke
```

Команда использует Gateway `18080` и Mailpit `18025`. Ожидается `PASS` и успешное завершение Go-тестов. Тест создаёт свои данные и проверяет реальный путь через сервисы, включая письмо. Это не нагрузочное испытание и не проверка отказа узла.

## Посмотреть состояние и найти ошибку

Все команды явно выбирают локальный kubeconfig и context:

```sh
kubectl --kubeconfig .local/kubeconfig --context kind-marketplace-example \
  -n marketplace get pods,jobs,pvc
kubectl --kubeconfig .local/kubeconfig --context kind-marketplace-example \
  -n marketplace logs deployment/marketplace-listings --tail=100
kubectl --kubeconfig .local/kubeconfig --context kind-marketplace-example \
  -n marketplace get events --sort-by=.lastTimestamp
```

`get` выводит состояние, `logs` — последние строки приложения, `events` — сообщения Kubernetes о запуске, образах и ресурсах. Эти команды ничего не перезапускают.

| Что видно | Как понять результат |
|---|---|
| Pod `Running`, `READY 1/1` | Контейнер работает и прошёл проверку готовности |
| Job `Complete` / его Pod `Completed` | Одноразовая задача успешно завершена; ей не нужно работать постоянно |
| PVC `Bound` | Для постоянных данных выделено хранилище |
| `Pending` | Смотрите Events: часто не хватает ресурсов или не удалось выделить хранилище |
| `CrashLoopBackOff` | Процесс падает повторно; начните с логов соответствующего приложения и миграции |
| `ErrImageNeverPull` / ошибка образа | В kind не найден локальный образ; проверьте успешность импорта, архитектуру и версию Docker |
| Ошибка или тайм-аут migration Job | Выберите фактическое имя Job из списка и прочитайте его логи; не продолжайте rollout без успешной миграции |

Для подробностей конкретного pod или Job используйте `kubectl ... describe pod ИМЯ` либо `kubectl ... logs job/ИМЯ`, сохраняя те же аргументы kubeconfig/context/namespace. `ИМЯ` нужно заменить на имя из фактического вывода; это схема команды, не готовый пример для копирования. У migration Job в имени есть ID запуска, поэтому старые неуспешные Jobs могут соседствовать с новой успешной попыткой.

Проверка `/health/ready` приложения в основном проверяет его соединение с БД; readiness Gateway не доказывает исправность всех зависимостей. После исправления повторите `make kind-up`, затем `make kind-smoke`. При повторном `kind-up` данные PVC остаются, но приложения будут перезапущены.

## Обновить код или проверить шаблоны

После изменения кода выполните из корня:

```sh
make kind-up
make kind-smoke
```

Первый шаг снова собирает и импортирует образы, выполняет миграции и заменяет работающие экземпляры. Одной пересборки через `make images` недостаточно: это ещё не импорт в узел kind.

Отдельно можно проверить шаблоны, не создавая кластер:

```sh
(cd tests/browser && npm ci)
make helm-check
```

Для этого нужны Node.js/npm и инструменты из `make tools`. Проверка включает Helm lint, проверки сгенерированных ресурсов и kubeconform. Скрипт сверяет схемы Kubernetes **1.35.0**; сам kind-скрипт создаёт узел **1.37.0**. Статическая проверка шаблонов не заменяет запуск в кластере и smoke.

## Ограничения локального варианта

- kindnet в данной конфигурации не применяет NetworkPolicy, поэтому политики выключены в [values.yaml](values.yaml). В основном chart входящие политики включены; проверять их нужно с CNI, который их поддерживает. CNI — сетевой компонент Kubernetes.
- PostgreSQL, Kafka и S3 используют PVC локального кластера. Перезапуск pod обычно сохраняет эти данные; удаление всего кластера — нет.
- Кластер и зависимости имеют по одному экземпляру. Успешный smoke не доказывает отказоустойчивость.
- Mailpit принимает только учебную почту. Это не доставка реальным пользователям.
- Секреты и пароли из `.local/.env` — локальное упрощение. Внешнее развёртывание требует собственных адресов, секретов и резервного копирования.

## Удалить учебный кластер — удаляет его данные

Если закончили упражнение и данные kind больше не нужны, команда ниже удалит **кластер `marketplace-example` вместе с его локальным хранилищем**. Сначала сохраните нужные данные. Это не обычная команда временной остановки:

```sh
.local/bin/kind delete cluster --name marketplace-example
```

Данные Compose и `.local/.env` сохраняются. Следующий `make kind-up` создаст новый кластер; демоданные нужно загрузить заново. Не удаляйте другие кластеры или пользовательские contexts для очистки этого стенда.
