# Локальная разработка и поиск ошибок

[К оглавлению](../README.md)

Эта инструкция относится к Docker Compose на вашем компьютере. Для первого знакомства начните с [README](../../README.md), для Kubernetes — с [инструкции kind](../../deploy/kind/README.md).

Все команды ниже вводятся в терминале **из корня репозитория** — папки с `Makefile` и `compose.yaml`. Терминал должен оставаться в этой папке, если явно не указано другое. Команды в блоках `sql` вводятся внутри программы `psql`; это не команды оболочки.

## Что находится на компьютере

| Название | Простое объяснение |
|---|---|
| Образ (image) | Собранная программа со всем необходимым для запуска |
| Контейнер (container) | Запущенный экземпляр образа |
| Том (volume) | Отдельное место для данных, которое переживает замену контейнера |
| Compose | Описание того, какие контейнеры и сети нужны приложению |
| Миграция | Изменение структуры базы: например, создание таблицы или колонки |
| `.local/.env` | Локальные пароли и ключи этого стенда; создаются через `make setup` |

`make setup` не меняет существующие ключи и пароли. При необходимости он добавляет недостающие `DEMO_PASSWORD` и `GRAFANA_PASSWORD`. Файл `.local/.env` не предназначен для публикации. Не прикладывайте его содержимое или полный вывод `docker compose config` к вопросу об ошибке: там есть секреты.

## Запуск и проверка состояния

```sh
make up
make seed
docker compose --env-file .local/.env ps -a
```

1. `make up` готовит локальные настройки, собирает образы и запускает зависимости, миграции и приложения. Команда ждёт готовности контейнеров.
2. `make seed` обращается к работающему API и добавляет Анну, Бориса и демонстрационные объявления. Это загрузка данных, а не запуск приложения. Повторный запуск обычно пропускает уже найденные объявления с теми же названиями; это не инструмент сброса или ремонта изменённых демоданных.
3. `ps -a` показывает также завершившиеся контейнеры. Для `migrate` и `kafka-init` состояние `Exited (0)` нормально: они выполняют одну задачу и завершаются. Для шести приложений ожидается работающий контейнер с успешной проверкой здоровья. `Exited (1)` у миграции означает ошибку.

Откройте [приложение](http://127.0.0.1:8080) и [почту Mailpit](http://127.0.0.1:8025). Mailpit собирает учебные письма; он не отправляет их в реальные почтовые ящики.

Проверить HTTP без браузера:

```sh
curl -i http://127.0.0.1:8080/health/ready
curl -fsS 'http://127.0.0.1:8080/api/v1/search?limit=20'
```

Первая команда печатает заголовки и ответ. Норма — HTTP `200` и `{"status":"ready"}`. Вторая показывает JSON выдачи поиска; сразу после публикации возможна небольшая задержка появления объявления.

**Readiness не проверяет весь стенд.** У сервисов с базой проверяется соединение с их PostgreSQL. У Gateway своей базы нет, поэтому его `200` не доказывает готовность Search, Kafka, S3 или SMTP. `/health/live` означает, что HTTP-процесс отвечает. Для проверки пользовательского сценария нужен `make smoke`.

## Как читать логи

```sh
docker compose --env-file .local/.env logs --tail=100 listings
docker compose --env-file .local/.env logs --since=5m gateway listings search
```

Первая команда показывает последние 100 строк одного сервиса; вторая — сообщения за последние пять минут у трёх сервисов. Чтение логов ничего не перезапускает. Если нужен непрерывный просмотр всех сервисов, выполните `make logs`. Завершите просмотр через `Ctrl+C`: контейнеры продолжат работать.

Для проблемного HTTP-запроса найдите `X-Request-ID` в заголовках ответа браузера или `curl -i`, затем ищите соответствующий `request_id` в JSON-логах. Не отправляйте другим людям заголовок `Authorization`, cookies и содержимое личной переписки. При включённой телеметрии поле `trace_id` помогает найти цепочку запроса в Jaeger. SQL spans не содержат текст запросов с пользовательскими аргументами.

## Что делать после изменения кода

После изменения только Listings:

```sh
docker compose --env-file .local/.env up -d --build --wait listings
docker compose --env-file .local/.env logs --tail=100 listings
```

`--build` собирает новый образ, `-d` оставляет контейнер работать в фоне, `--wait` ждёт готовности. Compose также может запустить необходимые зависимости. Замените `listings` на нужный сервис. Для обновления всего стенда используйте `make up`.

Обычный `restart` не пересобирает образ: новый исходный код сам по себе в контейнер не попадёт. Он подходит, когда нужно перезапустить прежнюю программу:

```sh
docker compose --env-file .local/.env restart listings
```

После изменения SQL-миграций сначала пересоберите инструмент миграции и примените изменения, затем обновите приложения:

```sh
docker compose --env-file .local/.env build migrate
make migrate
make up
```

SQL встроен в бинарный файл `migrate`, поэтому одного редактирования SQL недостаточно. Добавляйте новую миграцию вместо изменения уже применённой. При ошибке не продолжайте обновление вслепую: посмотрите вывод `make migrate` и проверьте состояние базы. Удаление тома — не обычный способ исправления миграции.

Сами базы и роли создаёт [init-postgres.sh](../../deploy/compose/init-postgres.sh) при первом запуске **пустого** тома PostgreSQL. Его редактирование не обновляет уже существующую базу. Это отдельный шаг от создания таблиц миграциями.

## Проверка данных без изменения

Подключиться к базе Listings:

```sh
docker compose --env-file .local/.env exec postgres psql -U listings -d listings
```

Вы попадёте в SQL-консоль. Здесь `-U` выбирает пользователя базы, `-d` — базу. Локальное подключение внутри контейнера позволяет не выводить пароль. Внешнее окружение может иметь другие правила доступа.

Посмотреть ещё не отправленные в Kafka события:

```sql
SELECT count(*) AS pending, min(created_at) AS oldest
FROM outbox WHERE sent_at IS NULL;
```

`pending = 0` означает, что сейчас нет ожидающих отправки событий. При этом Search ещё может обрабатывать уже доставленные в Kafka записи. Если число и возраст растут, переходите к [инструкции по событиям](events.md). Выйти из SQL-консоли: `\q`, затем Enter.

Состояния писем можно посмотреть одной командой из обычного терминала:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U notifications -d notifications \
  -c 'SELECT state, count(*) FROM jobs GROUP BY state;'
```

`pending` — ждёт попытки, `processing` — обрабатывается, `sent` — SMTP принял письмо, `failed` — автоматические попытки прекращены. Отсутствие строк означает отсутствие заданий. Значение `sent` само по себе не подтверждает прочтение или доставку реальному адресату.

Прямой SQL — инструмент администратора. Код приложения не должен читать чужие базы: сервисы взаимодействуют через API и события.

## Метрики и цепочки запросов

```sh
make observability-up
```

Команда добавляет средства наблюдения и включает отправку трассировок из приложений. Она может пересоздать контейнеры с новой конфигурацией; данные остаются в томах. Откройте:

| Инструмент | Адрес | Для чего нужен |
|---|---|---|
| Grafana | [127.0.0.1:13000](http://127.0.0.1:13000) | Графики состояния |
| Prometheus | [127.0.0.1:19090](http://127.0.0.1:19090) | Числовые показатели во времени |
| Jaeger | [127.0.0.1:16686](http://127.0.0.1:16686) | Путь отдельного запроса между сервисами |

После включения сделайте несколько новых запросов: старые трассировки задним числом не появятся. Метрики собираются с внутренних портов `9090`. Прочитать их напрямую:

```sh
docker compose --env-file .local/.env exec -T listings wget -qO- http://127.0.0.1:9090/metrics
```

`marketplace_outbox_pending` — число ожидающих событий, `marketplace_outbox_oldest_seconds` — возраст самого старого, `marketplace_consumer_lag` — отставание обработчиков, `marketplace_notification_jobs` — количество писем по состояниям.

При последующих обновлениях с сохранением наблюдаемости используйте оба файла Compose:

```sh
docker compose --env-file .local/.env -f compose.yaml -f compose.observability.yaml up -d --build --wait
```

Обычный `make up` использует только базовый файл и не включает настройки трассировки. Правила предупреждений Prometheus — примеры; Alertmanager и отправка уведомлений оператору не настроены. Grafana открыта анонимно с правами просмотра на локальном порту. Jaeger здесь не является долговременным архивом.

## Частые ошибки: что проверить первым

| Симптом | Что означает и что делать |
|---|---|
| `Cannot connect to the Docker daemon` | Docker не запущен. Запустите Docker Desktop/Engine, затем повторите `make up` |
| `port is already allocated` / `address already in use` | Порт занят. Посмотрите, какой ваш процесс использует порт; остановите ненужный экземпляр приложения. Не удаляйте данные ради освобождения порта |
| Нет `.local/.env` | Выполните `make setup`, затем повторите команду |
| `password authentication failed` после замены `.env` | Пароль в настройках отличается от сохранённого в томе. Верните прежний файл из защищённой копии; случайная повторная генерация не исправит существующую базу |
| Миграция завершилась с ошибкой | Посмотрите `docker compose --env-file .local/.env logs --tail=100 migrate`; приложение не должно запускаться поверх неизвестного состояния схемы |
| `502` или `504` от API | Gateway не смог получить ответ целевого сервиса. Проверьте `ps -a`, логи сервиса и его базу |
| `429` | Сработал лимит Gateway. Подождите время из `Retry-After` и уменьшите частоту запросов |
| Карточка изменилась, поиск ещё старый | Проверьте outbox, Kafka, lag и логи Search по [инструкции](events.md) |
| Сообщение видно, письма нет | Проверьте Messaging outbox, Notifications, состояния `jobs`, Accounts и Mailpit |
| Фото не открывается | Проверьте контейнер `storage`, адрес `S3_PUBLIC_ENDPOINT`, готовность фотографии и доступ к объявлению |

## Какие проверки запускать

| Команда | Что проверяет | Требования и побочные эффекты |
|---|---|---|
| `make lint` | Форматирование Go и `go vet` | Нужен Go; не меняет форматирование автоматически |
| `make test` | Go-тесты с проверкой гонок | Внешние сервисы не нужны; при первом запуске скачиваются модули |
| `make test-integration` | Реальные PostgreSQL/Kafka/S3 | Сначала `make up`; создаёт отдельные SQL-схемы для тестов и удаляет их после теста, также использует тестовые топики/объекты |
| `make smoke` | Сценарий через Gateway и Mailpit | Нужен работающий стенд; создаёт пользователей и объявления |
| `make test-browser` | Пользовательские действия в Chromium | Нужны Node.js/npm и браузер Playwright; создаёт учебные данные |
| `make contracts-check` | Согласованность контрактов | Сначала установите зависимости `tests/browser` |
| `make check` | `lint`, `test`, integration и smoke подряд | Нужен работающий стенд; браузерные, Helm и resilience проверки сюда не входят |
| `make test-resilience` | Восстановление после остановки Kafka/Search | **Останавливает контейнеры** проекта `marketplace`; только для отдельного упражнения |

Перед первым браузерным тестом из корня проекта:

```sh
(cd tests/browser && npm ci && npx playwright install chromium)
make test-browser
```

Скобки сохраняют текущую папку терминала. `make test-browser` повторно выполняет `npm ci` перед тестом. Для Go-команд напрямую можно использовать те же локальные кеши, что Makefile:

```sh
export GOCACHE="$PWD/.local/go-cache"
export GOMODCACHE="$PWD/.local/go-mod"
go test ./services/listings ./internal/platform/kafka
```

## Остановить работу и продолжить позже

```sh
make down
```

Контейнеры и сеть Compose удаляются, тома PostgreSQL/Kafka/S3 сохраняются. Следующий `make up` использует прежние данные. Если включали наблюдаемость, остановите полный набор:

```sh
docker compose --env-file .local/.env -f compose.yaml -f compose.observability.yaml down
```

Это сохраняет том Prometheus, но не обещает сохранение временных данных сервисов без постоянного тома, например истории писем Mailpit.

## Удалить данные и начать заново — разрушительное действие

**Следующая команда удаляет тома этого Compose-проекта:** аккаунты, объявления, переписку, фото, Kafka и историю Prometheus. Она нужна только для сознательно чистого учебного запуска. Для обычной ошибки или остановки её не используйте. Нужные данные сначала сохраните по [инструкции резервного копирования](deployment-and-backups.md).

```sh
docker compose --env-file .local/.env -f compose.yaml -f compose.observability.yaml down -v
make up
make seed
```

`.local/.env` и ранее созданные файлы резервных копий сохраняются. Не заменяйте `.local/.env` при сохранённых томах: настройки и реальные пароли перестанут совпадать. Глобальный `docker system prune` для очистки одного проекта не нужен.
