# События: отставание, ошибки, повтор и восстановление поиска

[К оглавлению](../README.md)

Все команды выполняются из корня репозитория на запущенном Compose-стенде (`make up`). Чтение логов, SQL `SELECT` и просмотр Kafka не меняют бизнес-данные. `replay`, `reindex` и SQL `UPDATE` ниже меняют состояние; у каждого действия указано назначение.

## Как изменение доходит до поиска или письма

После публикации объявления Listings сохраняет в одной транзакции карточку и запись **outbox** — «событие, которое надо отправить». Фоновый отправитель (**publisher**) передаёт событие в Kafka. Search читает его и обновляет собственную копию данных для поиска — **проекцию**. С сообщениями похожая цепочка: Messaging → outbox → Kafka → Notifications → задание на письмо → SMTP.

| Термин | Что это значит здесь |
|---|---|
| Topic, топик | Именованный журнал событий: `marketplace.listings.v1` для объявлений и `marketplace.messages.v1` для сообщений |
| Partition, раздел | Часть топика. В локальном стенде у основных топиков по три раздела. Номера записей считаются отдельно в каждом |
| Offset, смещение | Позиция записи внутри раздела. Позиция `10` в разделе `0` и позиция `10` в разделе `1` — разные записи |
| Consumer | Обработчик, который читает журнал |
| Consumer group, группа | Имя читателя, для которого Kafka хранит прогресс. Несколько экземпляров одной группы делят работу; разные группы читают независимо |
| Committed offset | Сохранённая позиция продолжения чтения: обычно номер **следующей** записи. После успешной обработки записи `10` сохраняется `11` |
| Lag, отставание | Сколько позиций отделяет группу от конца журнала; это не время задержки в секундах |
| Inbox | Список уже принятых `event_id` в Notifications; защищает от создания второго задания для того же события |
| DLQ | Отдельный топик для событий, которые обработчик признал некорректными. Сокращение от dead-letter queue |
| Replay | Повторная публикация выбранного события из DLQ |
| Reindex | Построение новой полной проекции Search из Listings с учётом событий Kafka |

Доставка допускает повторы. Если Kafka приняла событие, а отправитель не успел записать `sent_at` в outbox, событие будет опубликовано снова с прежним `event_id`. Search применяет только более новую версию объявления; Notifications проверяет inbox. Это не общая гарантия «ровно один раз»: SMTP может принять письмо до того, как приложение успеет сохранить `state='sent'`.

## Сначала найти, где остановилась цепочка

### 1. Проверить контейнеры и логи

```sh
docker compose --env-file .local/.env ps -a
docker compose --env-file .local/.env logs --since=5m listings messaging search notifications kafka
```

Повторяющиеся `event retry` означают, что обработчик не смог завершить запись и будет пробовать снова. Временные ошибки, например недоступность БД, повторяются с паузой от 1 до 30 секунд. Сам факт повторов не означает потерю события.

### 2. Проверить outbox отправителя

Для объявлений:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U listings -d listings \
  -c 'SELECT count(*) AS pending, min(created_at) AS oldest FROM outbox WHERE sent_at IS NULL;'
```

Для сообщений:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U messaging -d messaging \
  -c 'SELECT count(*) AS pending, min(created_at) AS oldest FROM outbox WHERE sent_at IS NULL;'
```

Норма после обработки — `pending = 0`, `oldest` пустое. Если число и возраст растут, проверьте Kafka, существование исходного топика и логи отправителя. Не выставляйте `sent_at` вручную: так событие можно пометить доставленным, хотя Kafka его не получила.

### 3. Проверить прогресс групп

```sh
docker compose --env-file .local/.env exec -T kafka \
  /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka:9092 --all-groups --describe
```

Команда выполняется внутри контейнера Kafka, поэтому адрес — `kafka:9092`. Для соединения с компьютера используется опубликованный `127.0.0.1:19092`; эти адреса не взаимозаменяемы.

Смотрите столбцы `GROUP`, `TOPIC`, `PARTITION`, `CURRENT-OFFSET`, `LOG-END-OFFSET`, `LAG`. Небольшое временное отставание при новых записях нормально. Устойчивый рост требует проверки. Отсутствие активных участников может означать остановленный сервис или старую группу, оставшуюся после переиндексации. `-` вместо позиции — не доказательство нулевого отставания.

До первой переиндексации Search использует `search-v1`; затем — `search-reindex-<UUID>`. Notifications использует `notifications-v1`. Узнать **текущую** группу Search:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U search -d search \
  -c 'SELECT p.id, p.group_id, p.ready FROM projections p JOIN settings s ON s.active_projection=p.id;'
```

Если outbox уже пуст, но lag текущей группы растёт, смотрите обработчик и его базу. Если lag нулевой, но результата нет, проверьте DLQ, нужный ID/версию объявления или очередь писем. Нулевой lag может означать и то, что некорректная запись перенесена в DLQ. Не исправляйте проблему ручным продвижением offsets: это может пропустить бизнес-изменение.

## Разобрать некорректное событие в DLQ

При некорректной оболочке события или несовместимом содержимом обычный consumer публикует исходную запись в DLQ. Только после успешной публикации он сохраняет прогресс исходного топика. Ошибка соединения с БД сама по себе не отправляет событие в DLQ.

Для стандартных групп имена такие:

- `marketplace.listings.v1.search-v1.dlq`;
- `marketplace.messages.v1.notifications-v1.dlq`.

После reindex у Search другой суффикс группы. Посмотреть доступные топики:

```sh
docker compose --env-file .local/.env exec -T kafka \
  /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka:9092 --list
```

Прочитать одну запись DLQ Notifications:

```sh
docker compose --env-file .local/.env exec -T kafka \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:9092 \
  --topic marketplace.messages.v1.notifications-v1.dlq \
  --from-beginning --max-messages 1 --timeout-ms 10000 \
  --property print.partition=true --property print.offset=true
```

Пустой топик может завершить чтение сообщением о тайм-ауте через 10 секунд: это не обязательно отказ Kafka. При нескольких разделах команда не обещает выбрать самое раннее событие по времени во всём топике. Она не изменяет прогресс групп Search или Notifications.

В выводе различайте два набора координат:

1. Напечатанные console consumer `Partition` и `Offset` — адрес **самой записи DLQ**.
2. Поля `topic`, `partition`, `offset` внутри JSON — адрес **исходной записи**. Поле `value` содержит строку исходного события, `key` — его ключ.

Для replay нужны координаты из пункта 1. Данные события могут содержать пользовательскую информацию; не публикуйте содержимое DLQ без проверки.

## Повторить одно событие — меняет журнал Kafka

Сначала исправьте причину: например, обновите несовместимый обработчик. Повтор неизменённого некорректного события не исправит данные. Если ошибка в самой оболочке события, инструмент может отказать ещё до публикации.

Следующий пример **нужно заполнить фактическими координатами**. Пустые значения намеренно не дают случайно отправить запись `0:0`. Введите эти строки в одной сессии терминала после просмотра DLQ:

```sh
dlq_topic='marketplace.messages.v1.notifications-v1.dlq'
dlq_partition=''
dlq_offset=''
```

Впишите в кавычки номер раздела и номер записи DLQ, затем выполните:

```sh
(
  : "${dlq_partition:?Укажите раздел записи DLQ}"
  : "${dlq_offset:?Укажите offset записи DLQ}"
  docker compose --env-file .local/.env --profile tools run --rm --build replay \
    --topic "$dlq_topic" --partition "$dlq_partition" --offset "$dlq_offset"
)
```

`--profile tools` включает вспомогательные программы, `run --rm` запускает одноразовый контейнер и убирает его после завершения, `--build` собирает актуальную версию инструмента. Скобки не позволяют проверке пустых переменных завершить весь ваш терминал.

Ожидаемый ответ — `Replayed event` и ID события. Инструмент ограничен 30 секундами. Он проверяет оболочку, публикует событие в исходный топик с прежним `event_id`, **не удаляет DLQ и не сбрасывает offsets**. `Requested record not available` означает, что точная запись по указанной позиции не найдена: проверьте координаты и срок хранения. Успешная публикация ещё не доказывает успешную последующую обработку: снова проверьте логи, lag и результат.

Replay не редактирует payload и не создаёт исправленный бизнес-факт. Если содержимое неверно, нужна обдуманная миграция или штатная операция сервиса. Повтор уже принятого Notifications события не создаст новое задание: inbox помнит `event_id`. Для неотправленного письма разбирайте `jobs`, а не повторяйте Kafka бесконечно.

## Полностью пересобрать поиск — создаёт и активирует новую проекцию

Используйте reindex, если нужна новая полная поисковая копия. Источник истины — Listings; Kafka локально хранит историю семь дней, поэтому простого чтения «с самого начала» может быть недостаточно. Для переиндексации нужны работающие Listings, Search, Search DB и Kafka.

Сначала сохраните для сравнения вывод запроса активной проекции из предыдущего раздела. Затем из корня проекта выполните:

```sh
docker compose --env-file .local/.env --profile tools run --rm --build reindex
```

Инструмент сам создаёт новый UUID. Дополнительный параметр `--projection` нужен только если вы хотите заранее выбрать **новый** UUID; обычно он не требуется. Не запускайте несколько перестроений одновременно без отдельного плана.

Что происходит:

1. Создаются новая группа `search-reindex-<UUID>` и её DLQ; сохраняются текущие конечные позиции Kafka.
2. Запускается чтение событий с этих позиций, чтобы не пропустить изменения во время импорта.
3. Из Listings постранично загружаются объявления со статусами `published` и `withdrawn`, включая их версии. Черновики в поиск не попадают.
4. Обработчик догоняет контрольную границу Kafka. Версии защищают от замены нового состояния старым.
5. После проверки готовности инструмент **сам переключает активную проекцию**. HTTP-поиск во время построения читает предыдущую. Search замечает переключение и продолжает чтение от имени новой группы.

Ожидаемый ответ — `Active projection:` и новый UUID. Лимит времени CLI — 30 минут. Это не обещание мгновенной актуальности при непрерывном потоке новых событий: обычная фоновая обработка продолжится после переключения.

Проверить результат:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U search -d search \
  -c 'SELECT p.id,p.group_id,p.ready FROM projections p JOIN settings s ON s.active_projection=p.id;'
curl -fsS 'http://127.0.0.1:8080/api/v1/search?limit=20'
```

В базе должен быть новый ID и `ready = t`; в поиске — ожидаемые опубликованные объявления. Сверьте хотя бы одну изменённую цену и отсутствие снятого объявления, затем проверьте lag новой группы.

При ошибке команда печатает `rebuild failed; previous projection preserved`. Некорректное событие при построении не пропускается через DLQ: перестроение прерывается, чтобы не активировать неполную копию. Удаление нужной истории Kafka во время импорта тоже приводит к ошибке. Исправьте причину и запустите новую попытку с новым ID. Незавершённая проекция, старые группы и DLQ могут остаться для разбора; автоматическая очистка не реализована.

Не переключайте `settings.active_projection` вручную на незавершённый результат. Простое возвращение старого ID тоже не является гарантированным откатом: старая проекция после переключения могла перестать получать события.

## Письмо не пришло: отдельная очередь Notifications

Проверьте [Mailpit](http://127.0.0.1:8025), логи Notifications и состояние заданий:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U notifications -d notifications \
  -c 'SELECT id, state, attempts, next_attempt, last_error FROM jobs ORDER BY created_at DESC LIMIT 20;'
```

Задание временно арендуется worker на 60 секунд: это позволяет другому worker продолжить его после зависания или падения первого. На обращение к Accounts и отправку выделено 20 секунд. Всего предусмотрено не более пяти попыток; после ошибок паузы составляют 10 секунд, 1 минуту, 5 минут и 30 минут. Ответ Accounts `404` или исчерпание попыток переводят задание в `failed`. Состояние `failed` автоматически обратно в очередь не возвращается.

`last_error` содержит техническую категорию без email и секретов. Проверьте доступность Accounts, service token и SMTP. Для остановленного в упражнении Mailpit достаточно:

```sh
docker compose --env-file .local/.env start mailpit
```

Если состояние ещё `pending`, дождитесь `next_attempt`. Если уже `failed`, после устранения причины можно вручную вернуть **одно проверенное** задание. Это административное действие и может повторно отправить письмо, которое SMTP уже принял до сбоя записи результата.

Откройте SQL-консоль:

```sh
docker compose --env-file .local/.env exec postgres psql -U notifications -d notifications
```

Внутри неё сначала выберите ID из `SELECT`. Затем замените текст в кавычках на этот UUID:

```sql
UPDATE jobs
SET state='pending', attempts=0, next_attempt=now(),
    lease_until=NULL, lease_owner=NULL, last_error=NULL
WHERE id='ВСТАВЬТЕ-ПРОВЕРЕННЫЙ-UUID' AND state='failed'
RETURNING id, state;
```

Ожидается ровно одна строка и `UPDATE 1`. `UPDATE 0` означает, что ID не найден или задание уже не `failed`: сначала перепроверьте состояние. Выйти: `\q`. Проверьте новое состояние и письмо. Не сбрасывайте все задания разом и не удаляйте inbox: это уничтожает защиту от повторных событий.
