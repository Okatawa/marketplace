# Как читать код и не потеряться

[К оглавлению](../README.md)

Начинайте с одного действия пользователя, а не со всех файлов подряд. Удобный первый вопрос: «Что произойдёт после нажатия “Опубликовать”?» Затем проследите путь от браузера до записи в БД и поискового каталога. [Обзор архитектуры](../architecture/overview.md) объясняет общую картину, эта страница показывает конкретные места в исходниках.

Ссылки ниже ведут на файлы. Внутри файла ищите указанное имя функции: номера строк меняются при редактировании, имена дают более устойчивый ориентир.

## Что означают папки

| Путь | Что искать |

| [`internal/platform/`](../../internal/platform) | Общие технические части: HTTP, токены, конфигурация, Kafka, outbox, наблюдаемость |
| [`services/gateway/web/`](../../services/gateway/web) | Браузерный интерфейс: HTML, CSS и обычный JavaScript |
| [`api/openapi.yaml`](../../api/openapi.yaml) | Описание HTTP API: методы, адреса, тела запросов и ответов |
| [`tests/`](../../tests) | Проверки взаимодействия частей системы и пользовательских сценариев |

| [`Makefile`](../../Makefile) | Короткие команды для запуска, проверок и других повторяемых действий |

### Почему go.mod один, а сервисов шесть

**Go module** — набор Go-пакетов с общим именем и списком зависимостей. В корне лежит один [`go.mod`](../../go.mod) с именем `example.com/marketplace`. Поэтому импорт `example.com/marketplace/services/listings` означает пакет из этого репозитория. Это имя пространства кода, а не адрес, по которому работающий сервис ходит в интернет.

**Пакет** объединяет Go-файлы одной папки. Например, `services/listings/handler.go`, `models.go` и `events.go` принадлежат `package listings` и могут использовать непубличные функции друг друга.

У каждой программы в `cmd/<имя>/main.go` свой `package main` и функция `main`. Сборка `./cmd/listings` создаёт программу Listings, сборка `./cmd/search` — Search. Один модуль облегчает совместную разработку: не нужно выпускать отдельные версии общих внутренних библиотек. Он не объединяет программы в один процесс и не делает их базы общими.

Название `internal` имеет смысл для Go: код этой области доступен пакетам внутри допустимого родительского дерева, а не произвольному стороннему проекту. Общая `platform` содержит технические средства; правила вроде «нельзя написать самому себе» остаются в конкретном сервисе.

## Несколько обозначений Go перед чтением

| Что встретится | Как читать |
| --- | --- |
| `func main()` | Начало выполнения программы |
| `type Service struct { ... }` | Тип с полями, например соединением с БД и конфигурацией |
| `func (s *Service) create(...) error` | Метод `create` объекта сервиса; возвращает ошибку или `nil` при успехе |
| `ctx context.Context` | Контекст операции: отмена, срок выполнения и технические данные, например связь с трассой |
| `http.Handler` | Объект, умеющий обработать HTTP-запрос |
| `r *http.Request` | Входящий запрос: адрес, заголовки, тело и контекст |
| `w http.ResponseWriter` | Средство записать HTTP-ответ |
| `pgxpool.Pool` | Пул — несколько переиспользуемых соединений с PostgreSQL |
| `if e != nil { return e }` | Если шаг не удался, прекратить операцию и вернуть ошибку выше |
| `defer ...` | Выполнить действие при выходе из функции, например закрыть результат SQL или отменить незавершённую транзакцию |
| `go func() { ... }()` | Запустить параллельно goroutine — лёгкую задачу внутри процесса Go |

Почти во всех обработчиках повторяется цепочка: прочитать ввод → проверить доступ → выполнить работу → вернуть JSON. JSON — текстовый формат объектов и массивов, которым обмениваются браузер и сервер.

## Маршрут 1. Как сервис вообще начинает работать

Откройте [`cmd/listings/main.go`](../../cmd/listings/main.go), функцию `main`. Она короткая: вызывает `app.Main`, подготавливает хранилище фотографий и возвращает HTTP-обработчик плюс две фоновые задачи — отправку outbox и очистку фото.

Затем откройте [`internal/platform/app/run.go`](../../internal/platform/app/run.go):

1. `Main` включает JSON-логи через `slog` и вызывает `run`.
2. `run` читает настройки через `config.Load`, создаёт контекст завершения процесса, включает наблюдаемость и соединяется с БД. У Gateway подключения к БД нет.
3. Переданная из `main` функция создаёт обработчики и список worker-ов. Здесь worker — функция, которая делает фоновую работу.
4. Worker-ы запускаются в goroutine. Если задача вернулась и приложение ещё работает, общий цикл запускает её снова после паузы. Поэтому временная ошибка Kafka не требует ручного перезапуска всей программы.
5. Запускаются сервер метрик, `/health/live`, `/health/ready` и основной HTTP-сервер.
6. При остановке контекст отменяется, фоновые задачи получают сигнал завершиться, соединения закрываются.

За настройками идите в [`config.Load`](../../internal/platform/config/config.go). За поведением HTTP-сервера и его завершением — в [`httpx.Run`](../../internal/platform/httpx/server.go).

Сравните точки входа остальных программ:

| Файл | Что добавляет к общему запуску |
| --- | --- |
| [`cmd/gateway/main.go`](../../cmd/gateway/main.go) | Маршрутизацию API и отдачу интерфейса |
| [`cmd/accounts/main.go`](../../cmd/accounts/main.go) | Обработчики аккаунтов, без собственных бизнес-worker-ов |
| [`cmd/messaging/main.go`](../../cmd/messaging/main.go) | Обработчики переписки и отправитель её outbox |
| [`cmd/search/main.go`](../../cmd/search/main.go) | Поисковый HTTP API и worker обновления проекции |
| [`cmd/notifications/main.go`](../../cmd/notifications/main.go) | Читатель событий и worker писем; пользовательского HTTP API нет |

Проверка понимания: почему код запуска и остановки не скопирован шесть раз? Потому что он общий, а фабрика, переданная в `app.Main`, выбирает только части нужного сервиса.

## Маршрут 2. От кнопки браузера до Listings

Начните с [`services/gateway/web/app.js`](../../services/gateway/web/app.js). `route` выбирает экран по части адреса после `#`. `editor` создаёт экран объявления; вложенные `save` и `action` отвечают за сохранение и действия формы. `catalog` выводит поиск, `listing` — отдельную карточку, `chat` — переписку.

В [`web/api.js`](../../services/gateway/web/api.js) функция `request` добавляет `/api/v1`, сериализует тело в JSON и прикладывает access token. При `401` она пытается обновить сессию через `refresh`, затем один раз повторяет запрос. Access token лежит в переменной модуля, а не в localStorage. Cookie обновления браузер передаёт самостоятельно.

Дальше запрос получает [`gateway.New`](../../services/gateway/router.go). Внутри видна таблица разрешённых публичных маршрутов и адресов назначения. `httputil.NewSingleHostReverseProxy` создаёт **обратный прокси** — посредника, который пересылает запрос сервису и возвращает его ответ браузеру. Например, `POST /api/v1/listings/{id}/publish` направляется в Listings.

Перед пересылкой Gateway ограничивает частоту запросов, убирает недоверенные служебные заголовки и проверяет переданный JWT. Счётчики ограничителя — локальная map в одном экземпляре Gateway, а не общая база лимитов.

В [`listings.New`](../../services/listings/handler.go) маршрут публикации связывается с `s.transition("published")`. `transition` читает `expected_version` и передаёт функцию изменения состояния в `change`. `change` выполняет основную работу.

Отдельно посмотрите [`httpx.Wrap` и `httpx.WriteError`](../../internal/platform/httpx/errors.go). Они позволяют обработчику просто вернуть `error`, а затем превращают её в единый JSON-ответ. Например, `httpx.Fail(409, "version", ...)` становится HTTP `409` с понятным кодом ошибки. Ошибка «строка не найдена» из pgx преобразуется в `404`.

## Маршрут 3. Где объявление становится строкой в БД

Сначала прочитайте [`services/listings/models.go`](../../services/listings/models.go):

- `Listing` описывает объявление, `Photo` — элемент списка фото, `Input` — входные поля изменения.
- Теги вида `json:"price_minor"` задают имя поля в JSON. `PriceMinor` — цена в копейках, целое число; браузер делит её на 100 для вывода рублей.
- `CanTransition` разрешает `draft → published`, `withdrawn → published` и `published → withdrawn`.
- `Validate` проверяет ограничения длины и цены. Для публикации дополнительно нужны название, описание, категория и хотя бы одно готовое фото.

Затем сравните модель с [`000001_listings.up.sql`](../../services/listings/migrations/000001_listings.up.sql). Это **миграция**, файл создания или изменения структуры БД. В нём видны таблицы, обязательные поля, допустимые статусы, индексы и внешние ключи. Дополнительная [`000002_outbox.up.sql`](../../services/listings/migrations/000002_outbox.up.sql) создаёт таблицу для событий.

Теперь прочитайте `create` в [`handler.go`](../../services/listings/handler.go). Он получает ID пользователя через `auth.Require`, читает JSON через `httpx.Decode`, проверяет модель и вставляет черновик. Затем `load` из [`repository.go`](../../services/listings/repository.go) читает сохранённое объявление с ID готовых фото. `scan` переносит столбцы результата SQL в поля структуры.

В этом учебном коде SQL находится и в `handler.go`, и в `repository.go`. Не ищите обязательную отдельную папку репозитория для каждого запроса: такого дополнительного слоя здесь нет. Параметры `$1`, `$2` и следующие передаются отдельно от SQL-текста.

### Прочитайте change по шагам

1. `auth.Require` устанавливает, что пользователь вошёл.
2. `db.Begin` начинает транзакцию; `defer tx.Rollback` гарантирует отмену, если функция завершится до успешного `Commit`.
3. `SELECT ... FOR UPDATE` читает и блокирует строку объявления.
4. Сравнение `OwnerID` проверяет права; сравнение `Version` и `expected` защищает от сохранения устаревшей версии.
5. `mutate(&l)` применяет конкретное изменение: новые поля или статус.
6. Запрос числа готовых фото и `Validate` проверяют итоговое состояние.
7. `l.Version++` и `UPDATE` сохраняют новую редакцию.
8. `s.emit` добавляет событие в ту же транзакцию, если объявление не черновик.
9. `tx.Commit` сохраняет оба изменения. Затем `s.get` возвращает карточку.

Обратите внимание на `&l`: функция изменения получает указатель на объявление и меняет именно его. Общая `change` помогает не копировать проверки владельца и версии отдельно для редактирования, публикации и снятия.

Проверка понимания: в какой точке можно вернуть `409`, не оставив частично обновлённую строку? До `Commit`; незавершённую транзакцию отменит `defer tx.Rollback`.

## Маршрут 4. От сохранённой публикации до поиска

После `change` откройте файлы в таком порядке:

| Файл и функция | На что смотреть |
| --- | --- |
| [`services/listings/events.go`, `emit`](../../services/listings/events.go) | Для `draft` сразу возвращается `nil`. Для остальных статусов собираются ID готовых фото и создаётся `listing.changed` |
| [`internal/platform/kafka/envelope.go`, `New`, `Envelope.Validate`](../../internal/platform/kafka/envelope.go) | Общий конверт события; отличие версии формата от версии объявления |
| [`internal/platform/outbox/publisher.go`, `Insert`](../../internal/platform/outbox/publisher.go) | Параметр `pgx.Tx`: вставка использует уже открытую транзакцию, а не новое независимое соединение |
| Там же, `Run` | Один активный отправитель, чтение неотправленной записи, публикация и лишь затем `sent_at` |
| [`internal/platform/kafka/transport.go`, `Producer.Publish`](../../internal/platform/kafka/transport.go) | ID объекта передаётся ключом Kafka, контекст трассы — заголовками |
| Там же, `Consumer.Run` | Чтение записи, проверка конверта, обработчик, сохранение offset; отдельно повторы и DLQ |
| [`services/search/worker.go`, `Run`](../../services/search/worker.go) | Читает активную проекцию и её группу, запускает обработку, обнаруживает смену проекции |
| [`services/search/projection.go`, `Projection.Apply`](../../services/search/projection.go) | Проверяет поля и применяет снимок только при новой версии |
| [`services/search/handler.go`, `New`](../../services/search/handler.go) | SQL выдачи выбирает активную проекцию, только опубликованные записи и подходящие фильтры |

Прочитайте конец SQL в `Projection.Apply`: `WHERE items.version < excluded.version`. Это короткое условие объясняет, почему повтор события не удваивает объявление, а старое событие не отменяет новое снятие с продажи.

В [`миграции Search`](../../services/search/migrations/000001_search.up.sql) найдите `document tsvector`, `to_tsvector('russian', ...)` и индекс `gin`. Они подготавливают слова из названия и описания для быстрого полнотекстового поиска средствами PostgreSQL. Сам запрос в обработчике использует `plainto_tsquery` и `ts_rank` для поиска и ранжирования.

Когда обычный поток уже понятен, прочитайте [`services/search/reindex.go`](../../services/search/reindex.go), функцию `Reindex`, вместе с [`cmd/reindex/main.go`](../../cmd/reindex/main.go). Отметьте две границы Kafka, параллельный импорт Listings и место переключения `settings.active_projection`. Подробное объяснение смысла этих шагов есть в [обзоре архитектуры](../architecture/overview.md).

## Маршрут 5. Сообщение и защита от повторной отправки

В [`services/messaging/handler.go`](../../services/messaging/handler.go) начните с `open`. Он ищет существующий диалог, а перед созданием нового получает объявление через `httpx.GetJSON` и проверяет продавца и статус. Это живой пример HTTP-связи двух сервисов без доступа к чужой БД.

Затем прочитайте `send`:

1. Берёт `Idempotency-Key` из заголовка и текст из JSON.
2. Открывает транзакцию и блокирует строку диалога.
3. Проверяет, что отправитель — покупатель или продавец этого диалога.
4. Ищет сообщение по сочетанию `conversation_id`, `sender_id`, `idempotency_key`. При совпадении тела возвращает старое сообщение, при отличии тела — `409`.
5. Вставляет новое сообщение, увеличивает версию диалога, определяет адресата.
6. Создаёт `message.created` с идентификаторами и записывает его в outbox перед `Commit`.

Сравните это с [`миграцией Messaging`](../../services/messaging/migrations/000001_messaging.up.sql): ограничение `UNIQUE(conversation_id,sender_id,idempotency_key)` дополнительно защищает уникальность на уровне БД.

Поле `seq bigserial` — последовательный числовой номер сообщения во всей таблице, а не отдельный счётчик внутри каждого диалога. `messages` выбирает сообщения данного диалога с `seq > cursor` в порядке `seq`. Поэтому номера внутри одного диалога могут иметь промежутки — это нормально.

В `participant` найдите общую проверку доступа к чтению. В `list` — запрос имени собеседника к Accounts и запасное имя «Пользователь», если профиль временно получить не удалось.

## Маршрут 6. Почему одно событие не создаёт два задания на письмо

Откройте [`notifications.Inbox.Accept`](../../services/notifications/inbox.go). Сначала проверяется событие, затем начинается транзакция. `INSERT INTO inbox ... ON CONFLICT DO NOTHING` добавляет ID события только впервые. Если строка не добавилась, функция возвращает `nil`: событие уже принимали. При первом приёме она создаёт `jobs` и сохраняет транзакцию.

Теперь [`notifications.Worker.Tick`](../../services/notifications/worker.go):

- выбирает готовое к отправке задание или задание с истёкшей арендой;
- устанавливает владельца аренды, срок и увеличивает число попыток;
- получает email у Accounts;
- вызывает интерфейс `Sender`;
- сохраняет результат, проверяя, что аренда всё ещё принадлежит этому worker-у.

**Интерфейс** `Sender` описывает необходимую способность — метод `Send`. Настоящий объект [`SMTP`](../../services/notifications/smtp.go) отправляет письмо, а тестовый объект может лишь посчитать вызовы или вернуть ошибку. Так тестируется обработка сбоев без реальной отправки почты.

Не объединяйте в голове две гарантии: уникальный inbox предотвращает второй `jobs` для того же события, но SMTP может принять письмо до сбоя записи `sent`. Тест [`TestNotificationsSMTPAcceptedThenDBFailure`](../../tests/integration/notification_recovery_test.go) специально показывает эту границу.

## Маршрут 7. Аккаунты, токены и права

Прочитайте [`services/accounts/service.go`](../../services/accounts/service.go): `ValidateRegistration`, `HashPassword`, `CheckPassword`. Затем в [`handler.go`](../../services/accounts/handler.go) — `register`, `login`, `respondSession`, `refresh` и `logout`.

Обратите внимание на разные секреты: пароль пользователя, случайный refresh token, закрытый ключ подписи JWT и общий сервисный токен имеют разные назначения. `newRefresh` создаёт случайное значение, `refreshHash` готовит хеш для БД, а `respondSession` возвращает access token и устанавливает cookie.

В [`internal/platform/auth/tokens.go`](../../internal/platform/auth/tokens.go):

- `Sign` подписывает JWT закрытым ключом Ed25519.
- `Verifier.Verify` проверяет подпись, срок, издателя и аудиторию токена.
- `Verifier.Optional` проверяет токен, если заголовок передан, и кладёт ID пользователя в контекст. «Optional» не означает «неверный токен допустим».
- `Require` требует пользователя в контексте.
- `Service` проверяет общий токен внутреннего HTTP API. Это другая проверка, не разбор пользовательского JWT.

После этого вернитесь в `Listings.change` и `Messaging.send`: именно там решается, имеет ли уже распознанный пользователь право менять объект. Проверка личности и проверка прав — разные шаги.

## Маршрут 8. Фотографии и два разных хранилища

В [`services/listings/media.go`](../../services/listings/media.go) прочитайте `ValidateImage`, `upload`, `removePhoto`, `photo` и `Cleanup`.

`upload` сначала создаёт `pending` в БД, затем пишет файл в S3. После этого транзакция переводит фото в `ready`, увеличивает версию объявления и при необходимости добавляет событие. Если операция оборвалась между шагами, остаются данные для последующей очистки.

`removePhoto` помечает запись `deleting`, а `Cleanup` позже удаляет объект из S3 и строку БД. Последнее фото опубликованного объявления удалить нельзя. `Media.URL` создаёт временную подписанную ссылку, `photo` перенаправляет браузер на неё после проверки доступа.

Упражнение на понимание: найдите, почему нельзя заменить все эти состояния одним `INSERT` в SQL. SQL-транзакция не может автоматически отменить уже выполненный `PutObject` в другом хранилище.

## Маршрут 9. Логи и измерения

В [`internal/platform/telemetry/telemetry.go`](../../internal/platform/telemetry/telemetry.go) прочитайте `Init`, `WrapHTTP` и методы `SQLTracer`. В [`backlog.go`](../../internal/platform/telemetry/backlog.go) — сбор размеров очередей и отставания Kafka. `slog.SetDefault` ищите в [`app.Main`](../../internal/platform/app/run.go).

Логи — JSON-записи в stdout. OpenTelemetry traces — связанные участки работы; контекст передаётся через HTTP, outbox и Kafka. Метрики — числовые показатели. Это три разных потока, хотя они помогают разбирать одну проблему. [`otel-collector.yaml`](../../deploy/observability/otel-collector.yaml) сейчас настраивает только traces; наличие `slog` не означает автоматический экспорт логов в Collector.

Найдите `trace_id` в HTTP-логе и `headers` в `outbox.Insert`. Затем посмотрите [`миграцию Notifications`](../../services/notifications/migrations/000001_notifications.up.sql): у `jobs` нет поля контекста трассы, поэтому позже запущенный worker письма автоматически не продолжает исходный trace сообщения.

## Миграции, команды и тесты как дополнительная документация

Файлы `migrations/*.up.sql` изменяют структуру вперёд, `*.down.sql` описывают обратное действие. [`cmd/migrate/main.go`](../../cmd/migrate/main.go) выбирает миграции сервиса и вызывает `m.Up()`. SQL встроен в Go-программы через `go:embed` в файлах `services/<сервис>/migrations.go`. Обычный запуск HTTP-сервиса не заменяет отдельный шаг применения миграций.

Из вспомогательных программ полезно прочитать:

| Файл | Назначение |
| --- | --- |
| [`cmd/devsetup/main.go`](../../cmd/devsetup/main.go) | Подготовка локальных настроек |
| [`cmd/seed/main.go`](../../cmd/seed/main.go) | Заполнение демонстрационными данными через API |
| [`cmd/reindex/main.go`](../../cmd/reindex/main.go) | Полная перестройка поисковой копии с автоматическим переключением после проверки |
| [`cmd/replay/main.go`](../../cmd/replay/main.go) | Чтение конкретной записи DLQ и повторная публикация её события в исходный топик |

Тест часто объясняет правило лучше длинного комментария: видны исходные условия, действие и ожидаемый результат. Хороший порядок чтения:

## Небольшие учебные задания

Начните с чтения и предсказания результата. Проверки через работающий API выполняйте на собственных тестовых данных в локальной среде.

1. **Нарисуйте путь публикации.** Выпишите по порядку `request → gateway.New → transition → change → emit → outbox.Insert`. Возле каждого имени укажите: «проверяет», «сохраняет» или «направляет». Затем добавьте отдельную фоновую цепочку до `Projection.Apply`.
2. **Разберите две вкладки.** Обе видели версию `7`; первая успешно сохранила изменение. Найдите в коде, какой ответ получит вторая с `expected_version: 7` и почему данные первой сохранятся.
3. **Предскажите поисковую копию.** Мысленно примените версии `4/published`, `6/withdrawn`, `4/published`, `6/withdrawn`. Какой результат останется? Найдите одно SQL-условие, которое это обеспечивает.
4. **Различите три идентификатора.** Для сообщения найдите клиентский `Idempotency-Key`, созданный сервером `message_id` и `event_id` события. Объясните, какой из них предотвращает второе сообщение, а какой — второе задание на email.
5. **Проследите один 404.** Найдите SQL-чтение отсутствующей строки и место, где `pgx.ErrNoRows` становится публичным ответом. Почему обработчик не пишет этот JSON самостоятельно?
6. **Найдите границы транзакций.** Для объявления, сообщения и задания письма выпишите, что находится между `Begin` и `Commit`. Отдельно отметьте действия Kafka, S3 и SMTP, которые не входят в эти транзакции.
7. **Объясните необходимость reindex.** Возьмите объявление, опубликованное месяц назад без последующих изменений. Сможет ли новый Search восстановить его только по Kafka с семидневным хранением? Найдите другой источник данных в `Reindex`.
8. **Разберите отказ без запуска сбоя.** Прочитайте тест про «SMTP принял письмо, БД не сохранила результат». Предскажите число отправок после повторного выполнения. Затем сравните с утверждениями теста.

Если можете пройти оба пути — «публикация → поиск» и «сообщение → задание → письмо» — и назвать места, где допустим повтор, основная связность этого проекта уже понятна. Для дальнейшей практики есть [упражнения со сбоями](../exercises/failures.md); они отдельно предупреждают, какие действия меняют состояние окружения.
