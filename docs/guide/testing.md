# Как читать и запускать тесты

[К оглавлению](../README.md)

В проекте несколько уровней проверок. Они отвечают на разные вопросы: правильно ли работает отдельная функция, согласованно ли работают обработчик и PostgreSQL, проходит ли пользовательский путь через реальные контейнеры, переживает ли доставка событий остановку брокера. Успешный `make test` не означает, что уже проверены Kafka, браузер и развёртывание.

Команды ниже выполняются из корня репозитория. Их точное определение находится в [`Makefile`](../../Makefile), а порядок автоматических проверок — в [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml). Для Go ориентируйтесь на используемую проектом версию 1.27.1; `go.mod` задаёт минимальный уровень языка 1.27.0. В CI используется Node.js 24. Установка Go/npm-зависимостей, браузера и инструментов может потребовать сеть.

## Карта проверок

| Команда | Что проверяет | Что должно работать | Что изменяет |
|---|---|---|---|
| `make lint` | Форматирование Go и проверки `go vet` | Go | Кеши Go; исходники не форматирует автоматически |
| `make test` | Обычные Go-тесты с `-race` | Go; Docker не нужен | Кеши Go и временные тестовые файлы |
| `make test-integration` | Обработчики и хранилища, Kafka, outbox, проекции, восстановление заданий | PostgreSQL, Kafka с топиками, S3, `.local/.env` | Тестовые схемы БД, S3 buckets/объекты, Kafka-записи и временные топики |
| `make smoke` | Полный путь публикация → поиск → сообщение → письмо | Весь Compose-стенд, включая Mailpit | Новые аккаунты, объявление, фото, диалог, сообщение, письмо |
| `make test-browser` | Поведение веб-интерфейса в Chromium | Весь стенд, Node.js/npm, установленный Chromium Playwright | Пользовательские данные, письмо, скриншот, файлы Playwright и `node_modules` |
| `make test-resilience` | Публикация при остановленной Kafka и догоняющий Search | Весь локальный Compose-стенд, Docker CLI | Останавливает/запускает Kafka и Search; создаёт пользовательские данные |
| `make contracts-check` | Структура OpenAPI и отдельных JSON Schema событий | Node.js и зависимости `tests/browser` | Стенд не изменяет |
| `make helm-check` | Рендер Helm, свойства манифестов и Kubernetes-схемы | Helm, kubeconform, Node.js и зависимости `tests/browser` | Файлы `.local/helm-*.yaml`; ничего не применяет к кластеру |
| `make kind-smoke` | Тот же smoke через Gateway локального kind | Уже поднятый kind-стенд и доступные порты | Данные приложения внутри kind |

`make check` запускает только `lint`, `test`, `test-integration`, `smoke`. Он не устанавливает и не поднимает зависимости и не включает браузер, resilience, contracts или Helm. Для последовательного учебного запуска не используйте `make -j`: одновременная остановка Kafka и smoke создаст ложные сбои.

## 1. Начать с проверок без инфраструктуры

```sh
make lint
make test
```

`make lint` выполняет проверку `gofmt -l` и затем `go vet ./...`. Если форматирование нарушено, цель завершится ошибкой; автоматического исправления в ней нет.

`make test` — это `go test -race ./...`. Файлы с `//go:build integration`, `smoke` и `resilience` исключены из обычного запуска. `-race` ищет гонки доступа к памяти в реально выполненных ветвях; это не доказательство отсутствия всех возможных гонок. Для race detector нужен поддерживаемый Go платформой C toolchain.

Что стоит прочитать первым:

| Файлы | Учебный смысл |
|---|---|
| [`services/listings/service_test.go`](../../services/listings/service_test.go) | Допустимые переходы статусов и обязательные поля опубликованного объявления |
| [`services/listings/media_test.go`](../../services/listings/media_test.go) | Настоящий PNG принимается; поддельный MIME и слишком большой файл отклоняются |
| [`services/accounts/service_test.go`](../../services/accounts/service_test.go) | Валидация регистрации, хеширование и проверка пароля |
| [`internal/platform/auth/tokens_test.go`](../../internal/platform/auth/tokens_test.go) | Валидность JWT и отклонение неподходящего алгоритма |
| [`services/gateway/router_test.go`](../../services/gateway/router_test.go) | Разрешённые маршруты, удаление поддельных служебных заголовков, rate limit, формат ошибок, источник фото в CSP |
| [`internal/platform/httpx/errors_test.go`](../../internal/platform/httpx/errors_test.go), [`server_test.go`](../../internal/platform/httpx/server_test.go) | Идентификатор запроса в ошибке и корректное завершение HTTP-сервера |
| [`internal/platform/telemetry/telemetry_test.go`](../../internal/platform/telemetry/telemetry_test.go) | Секретные значения из проверяемого HTTP-запроса не попадают в лог |
| [`internal/platform/kafka/envelope_test.go`](../../internal/platform/kafka/envelope_test.go) | Неверная оболочка события отклоняется до прикладной обработки |
| [`cmd/devsetup/main_test.go`](../../cmd/devsetup/main_test.go) | Повторная настройка сохраняет существующие секреты и добавляет отсутствующие |

Не все обычные тесты — буквально «одна чистая функция»: например, Gateway использует тестовые HTTP-серверы. Общая граница здесь — отсутствие внешнего Docker-стенда.

Для изучения одной проверки удобно запускать её отдельно:

```sh
GOCACHE="$PWD/.local/go-cache" GOMODCACHE="$PWD/.local/go-mod" \
  go test -race ./services/listings -run '^TestCanTransition$' -v -count=1
```

Переменные кеша соответствуют Makefile. `-v` показывает имена тестов, `-run` выбирает тест по регулярному выражению, `-count=1` отключает повторное использование сохранённого результата теста. Пакетный кеш компиляции при этом остаётся полезным.

## 2. Подключить PostgreSQL, Kafka и S3

Для интеграционных тестов не обязательно запускать все микросервисы:

```sh
make infra-up
make test-integration
```

`infra-up` сначала выполняет `setup`, затем запускает PostgreSQL, Kafka, инициализацию топиков, S3-хранилище и Mailpit. В отличие от `make up`, эта цель не передаёт Compose флаг `--wait`: сразу после первого старта зависимости могут ещё прогреваться. Состояние можно посмотреть командой:

```sh
docker compose --env-file .local/.env ps -a
```

Дождитесь готовности PostgreSQL, Kafka и storage и успешного завершения `kafka-init`. Если всё приложение уже запущено через `make up`, дополнительно выполнять `infra-up` не нужно.

В [`tests/integration/helpers_test.go`](../../tests/integration/helpers_test.go) видно, как устроена изоляция. Тест читает только необходимые значения из `.local/.env`, подключается к нужной базе на `localhost:15432`, создаёт уникальную схему `test_*`, устанавливает `search_path` и применяет миграции сервиса. При нормальном завершении `t.Cleanup` удаляет эту схему. Большинство запросов обращается к обработчикам через `httptest`, без публичного Gateway и контейнера соответствующего сервиса. JWT-ключи для них генерируются отдельно.

Это важно для интерпретации результата: успешный тест обработчика подтверждает его работу с реальной БД, но не подтверждает корректность адресов контейнеров, настройки Gateway или работу браузера. Для этого нужны следующие уровни.

### Какие свойства проверяются

| Тесты в `tests/integration/` | Что именно подтверждают |
|---|---|
| [`accounts_test.go`](../../tests/integration/accounts_test.go) | Регистрация, приватный email, отказ при неверном пароле; из двух одновременных refresh старой cookie успешен один; чужой Origin отклоняется; logout отзывает сессию |
| [`listings_test.go`](../../tests/integration/listings_test.go) | Чужой черновик скрыт, чужое изменение запрещено, устаревшая версия даёт конфликт, без фото публикация запрещена |
| [`media_test.go`](../../tests/integration/media_test.go) | Реальная загрузка PNG в S3, увеличение версии, публикация и её outbox-запись; последнее фото опубликованной карточки нельзя удалить |
| [`messaging_test.go`](../../tests/integration/messaging_test.go) | Повторное открытие возвращает тот же диалог; посторонний не читает историю; повтор ключа возвращает то же сообщение; другой текст с тем же ключом конфликтует; outbox не содержит текст сообщения |
| [`search_test.go`](../../tests/integration/search_test.go), [`search_validation_test.go`](../../tests/integration/search_validation_test.go) | Применяется только более новая версия; старое событие не возвращает снятое объявление; неверные снимки не заменяют корректное видимое состояние; фильтры работают |
| [`reindex_test.go`](../../tests/integration/reindex_test.go) | Сборка и переключение поисковой проекции; снятие во время перестроения не теряется; ошибка экспорта сохраняет старую проекцию; неверное живое событие не позволяет активировать новую |
| [`transport_test.go`](../../tests/integration/transport_test.go) | Контекст трассировки проходит через настоящий Kafka; испорченная запись сохраняется в DLQ с исходными координатами и байтами; неуспешная обработка не коммитит offset и событие приходит повторно |
| [`outbox_test.go`](../../tests/integration/outbox_test.go) | Kafka уже приняла событие, но БД не дала отметить его отправленным: повторная публикация сохраняет тот же `event_id` |
| [`notifications_test.go`](../../tests/integration/notifications_test.go) | Дубликат события не создаёт второе задание; после пяти неудачных попыток отправка прекращается |
| [`notification_recovery_test.go`](../../tests/integration/notification_recovery_test.go) | Просроченная аренда задания освобождается; исчерпавшее попытки задание становится `failed`; принятие SMTP до сбоя записи в БД может привести к повторному письму |

В тестах Notifications SMTP заменён объектом-заглушкой. Он позволяет точно воспроизвести границу сбоя, но не проверяет доставку через Mailpit. Это делает smoke.

### Что остаётся после интеграционного запуска

Изоляция схем PostgreSQL не означает, что интеграционный набор полностью изолирован от общего стенда:

- Транспортные и outbox-тесты создают уникальные Kafka-топики и затем пытаются удалить их. Принудительное завершение процесса может помешать очистке.
- Тесты переиндексации публикуют события в общий `marketplace.listings.v1`. Если Search приложения запущен, он тоже увидит их; ошибочное событие может попасть в его DLQ. Тестовые UUID не совпадают с обычными объявлениями, но записи Kafka не «откатываются» удалением тестовой схемы.
- Проверка фото создаёт уникальный S3 bucket `test-*` и объект. В текущем тесте нет очистки этого bucket после завершения.
- Аварийное завершение до `t.Cleanup` может оставить схему `test_*`. Не очищайте все похожие объекты в общем окружении: эти команды предназначены для своего локального учебного стенда.

Запуск отдельного интеграционного теста после подготовки инфраструктуры:

```sh
GOCACHE="$PWD/.local/go-cache" GOMODCACHE="$PWD/.local/go-mod" \
  go test -tags=integration ./tests/integration \
  -run '^TestMessagingPrivacyAndIdempotency$' -v -count=1
```

## 3. Проверить полный путь через контейнеры

```sh
make up
make smoke
```

[`tests/smoke/marketplace_test.go`](../../tests/smoke/marketplace_test.go) создаёт продавца и покупателя с уникальными адресами, загружает фото, публикует объявление, ждёт его в поиске, открывает диалог, отправляет сообщение и читает историю продавцом. Затем через HTTP API Mailpit ищет письмо нужному адресату и проверяет, что в нём есть ссылка на диалог, но нет текста сообщения.

Здесь работают реальные сервисы, S3, Kafka, outbox и SMTP. На появление объявления отведено до 40 секунд ожидания, на письмо — ещё до 40 секунд; это пределы ожидания отдельных этапов, а не обещание длительности всего теста. Нет жёсткого `sleep`, после которого результат просто считается готовым: тест опрашивает состояние.

По умолчанию используются `BASE_URL=http://127.0.0.1:8080` и `MAILPIT_URL=http://127.0.0.1:8025`. Для уже поднятого kind есть отдельная цель:

```sh
make kind-smoke
```

Она запускает тот же тест с адресами `127.0.0.1:18080` и `127.0.0.1:18025`. Подготовка кластера описана в [`deploy/kind/README.md`](../../deploy/kind/README.md). `kind-smoke` сам кластер не создаёт.

Smoke оставляет аккаунты, опубликованное объявление, файл, диалог и письмо. Это полезно для ручного осмотра, но после многих запусков каталог накопит тестовые данные. `make down` сохраняет их в томах. Безопасное различие остановки и полной очистки разобрано в [локальной разработке](../runbooks/local-development.md).

## 4. Проверить браузер

При первой подготовке:

```sh
(cd tests/browser && npm ci && npx playwright install chromium)
make test-browser
```

На Linux может понадобиться установка системных зависимостей браузера: CI использует `npx playwright install --with-deps chromium`. Эта команда может устанавливать системные пакеты; это отдельный шаг подготовки окружения.

`make test-browser` каждый раз выполняет `npm ci`, затем `npx playwright test`; сам Chromium эта цель не устанавливает. Фиксация зависимостей находится в `tests/browser/package-lock.json`. Настройки [`tests/browser/playwright.config.js`](../../tests/browser/playwright.config.js): один worker, headless-браузер, таймаут отдельного теста 90 секунд, базовый URL из `BASE_URL` либо `http://127.0.0.1:8080`.

В [`tests/browser/marketplace.spec.js`](../../tests/browser/marketplace.spec.js) три сценария:

1. Задержанный ответ на отправку сообщения не стирает следующий набранный черновик, а повторное нажатие не создаёт вторую отправку. API здесь подменяется тестом.
2. Несколько параллельных `401`, включая поздно пришедший ответ, приводят к одному обновлению сессии. Проверяется клиентский `api.js` с подменённым `fetch`.
3. Через реальное приложение создаются два пользователя, объявление с фото и переписка в обе стороны; HTML-подобный заголовок отображается как текст; после искусственного `500` введённая форма сохраняется; снятое объявление исчезает из поиска.

Таким образом, браузерный набор сочетает целевые клиентские проверки с реальным сквозным сценарием. Он сохраняет `.local/chat-desktop.png`; тестовые пользователи и сообщения остаются, а объявление основного сценария в конце снято с продажи. Playwright также может оставлять результаты в `tests/browser/test-results`. Скриншот — дополнительный материал для просмотра, а не тест визуального совпадения с эталоном.

## 5. Проверить восстановление после остановки компонентов

Запускайте отдельно от smoke и браузерных сценариев, когда допустимо на короткое время остановить локальные Kafka и Search:

```sh
make test-resilience
```

[`tests/resilience/recovery_test.go`](../../tests/resilience/recovery_test.go) работает именно с Compose-проектом этого репозитория и адресом `http://127.0.0.1:8080`. Переменная `BASE_URL` этот тест не перенаправляет.

Он создаёт объявление с фото, останавливает Search и Kafka, публикует объявление и проверяет, что карточка продолжает читаться. Затем запускает Kafka, ждёт ответа брокера, запускает Search и проверяет появление объявления в поиске. Это демонстрация того, что синхронная публикация опирается на БД и outbox, а доставка в поиск может догнать состояние позже.

Тест регистрирует `t.Cleanup`, который пытается запустить остановленные контейнеры при завершении. Если процесс теста был убит или Docker недоступен, автоматическая очистка не гарантирована. Для восстановления проверьте состояние и запустите сервисы:

```sh
docker compose --env-file .local/.env ps -a
docker compose --env-file .local/.env start kafka search
```

Проверка не имитирует потерю диска, уничтожение томов, сетевое разделение кластера или отказ машины с PostgreSQL. Она не доказывает высокую доступность инфраструктуры с одним узлом. После неё остаётся опубликованное тестовое объявление.

## 6. Проверить описания контрактов и Helm

Эти проверки можно выполнять без работающего приложения:

```sh
(cd tests/browser && npm ci)
make contracts-check
make tools
make helm-check
```

`make contracts-check` запускает [`tests/browser/check-contracts.mjs`](../../tests/browser/check-contracts.mjs). Скрипт валидирует OpenAPI, проверяет, что явно перечисленные публичные маршруты Gateway описаны в спецификации, читает схемы событий и сверяет допустимые поля payload события сообщения. Он не отправляет HTTP-запросы и не сравнивает каждый реальный ответ с JSON Schema. Для согласования спецификации с поведением нужны также код и интеграционные тесты.

`make tools` скачивает Helm и kind в `.local/bin`, проверяет их опубликованные контрольные суммы, устанавливает kubeconform через Go; для скрипта нужны `curl`, Python 3, `tar` и сеть. Он не создаёт кластер. Если совместимые Helm и kubeconform уже доступны, подготовку инструментов можно не повторять.

[`scripts/check-helm.sh`](../../scripts/check-helm.sh) выполняет:

1. `helm lint` и рендер обычного chart с Ingress и миграциями.
2. Проверки количества Deployment/Job, probes, ресурсов, ограничений контейнеров, ссылок на секреты, NetworkPolicy и TLS в Ingress через [`tests/browser/check-helm.mjs`](../../tests/browser/check-helm.mjs).
3. Валидацию kubeconform для Kubernetes 1.35.0.
4. Отдельный рендер и проверку схем конфигурации kind.
5. Рендер фазы только миграций, проверку, что она содержит пять Job, и проверку их схем.

Результаты записываются в `.local/helm-rendered.yaml`, `.local/helm-kind.yaml`, `.local/helm-migrations.yaml`. Секреты должны существовать отдельно; chart не рендерит их значения. Скрипт ничего не применяет через `kubectl`. Схемы kubeconform при отсутствии кеша могут потребовать сеть.

Успешный рендер не проверяет доступность образов, реальные сетевые политики, пароли к внешним зависимостям или прохождение миграций в кластере. Для этого нужен запуск окружения и `kind-smoke`.

## Рекомендуемый порядок и разбор падения

Для первой полной проверки удобно идти последовательно: `make lint`, `make test`, подготовка инфраструктуры и `make test-integration`, затем `make up`, `make smoke`, браузер и в конце resilience. Contracts и Helm можно проверить отдельным блоком без стенда. Скачивание зависимостей и сборка образов часто занимают больше времени, чем сами обычные тесты; конкретного общего времени репозиторий не гарантирует.

Если тест упал, сначала прочитайте имя проверки и её первое содержательное сообщение. Не повторяйте весь набор без понимания причины:

| Симптом | Следующий шаг |
|---|---|
| `connection refused`, создание схемы не удалось | Проверить Docker и PostgreSQL на `15432`, наличие `.local/.env`, готовность контейнеров |
| Ошибка загрузки фото | Проверить storage на `9000`, его готовность и настройки, не выводя секреты |
| Объявление не появилось в Search | Проверить Kafka, outbox-публикатор Listings, Search и его DLQ; см. [события](../runbooks/events.md) |
| Сообщение читается, но письма нет | Проверить Notifications, задания и Mailpit на `8025`; HTTP-успех сообщения не означает уже доставленное письмо |
| `429` после серии запусков | Дождаться обновления минутного окна Gateway; особенно ограничены маршруты авторизации |
| Playwright не запускает браузер | Установить Chromium и его системные зависимости, проверить `BASE_URL` |
| Helm/Node command not found | Подготовить `.local/bin` через `make tools` и зависимости `tests/browser` |
| Resilience прерван | Проверить, что Kafka и Search снова запущены |

Не публикуйте `.local/.env`, cookie-файлы, JWT и строки подключения вместе с отчётом. Для повторяемого отчёта достаточно команды, версии инструментов, результата, имени упавшего теста и очищенного от секретов сообщения об ошибке. Сведения о ранее выполненных проверках проекта лежат в [`docs/verification.md`](../verification.md); они не заменяют запуск в вашем окружении.
