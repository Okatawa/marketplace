# Упражнения: понять поведение приложения через небольшие сбои

[К оглавлению](../README.md)

Здесь можно увидеть, зачем нужны отдельные сервисы, outbox, версии данных и повторные попытки. Выполняйте упражнения **только на своём локальном Compose-стенде**, последовательно, с отдельными учебными объявлениями. Не запускайте параллельно тесты или демонстрацию, которым нужны доступные сервисы.

Все команды выполняются в терминале из корня репозитория. Подготовка:

```sh
make up
make seed
```

Откройте [приложение](http://127.0.0.1:8080) и [Mailpit](http://127.0.0.1:8025). Для двух пользователей удобно использовать обычное и приватное окно браузера: Анна `anna@example.com` продаёт, Борис `boris@example.com` покупает. Пароль обоих — `DEMO_PASSWORD` в `.local/.env`. При желании включите графики командой `make observability-up`.

Команда `stop` ниже временно останавливает выбранный контейнер и сохраняет данные; парная команда `start` возвращает его. Эти упражнения не требуют `down -v`, удаления таблиц или изменения offsets. Если прервали упражнение посередине, сначала верните остановленные компоненты:

```sh
docker compose --env-file .local/.env start kafka search mailpit
```

Затем проверьте `docker compose --env-file .local/.env ps -a`. Сохранение томов не означает, что кратковременной недоступности не будет: часть страниц и писем во время упражнения намеренно перестанет работать.

## 1. Одно изменение видно в двух местах не одновременно

**Что изучаем:** Listings хранит исходное объявление, Search — отдельную копию для каталога. Их обновление не происходит одной общей транзакцией.

1. Под Анной создайте и опубликуйте отдельное объявление с фотографией и запоминающимся названием.
2. Под Борисом найдите его в каталоге.
3. Под Анной измените цену и сохраните. Сразу откройте карточку, затем обновите каталог Бориса.
4. Снимите объявление с продажи и снова обновите каталог.

**Ожидаем:** сохранённая карточка показывает новую цену; каталог догоняет изменение после события. Задержка может быть слишком короткой, чтобы заметить её вручную. После снятия объявление перестаёт попадать в поиск, но его состояние сохраняется в Listings. Уже существующая переписка не удаляется.

**Где читать:** [обработчик Listings](../../services/listings/handler.go), [проекция Search](../../services/search/projection.go), [миграция Search](../../services/search/migrations/000001_search.up.sql). Найдите изменение `version`, событие `listing.changed` и условие применения только более новой версии.

**Проверочный вопрос:** зачем Search хранит версию снятого объявления, вместо того чтобы просто забыть строку? Она не позволяет старому событию публикации снова вернуть товар в выдачу.

**Если каталог не догоняет:** проверьте outbox, активную группу Search и lag по [инструкции](../runbooks/events.md). Не меняйте повторно цену только ради «проталкивания» события.

## 2. Kafka выключена, а публикация сохраняется

**Что изучаем:** успешная запись объявления в БД не зависит от немедленной доступности брокера событий.

1. Создайте под Анной **черновик** и загрузите фотографию. Пока не публикуйте его.
2. В терминале остановите только Kafka:

```sh
docker compose --env-file .local/.env stop kafka
```

3. Опубликуйте подготовленный черновик в браузере. Посмотрите его карточку.
4. Проверьте очередь неотправленных событий Listings:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U listings -d listings \
  -c 'SELECT count(*) AS pending, min(created_at) AS oldest FROM outbox WHERE sent_at IS NULL;'
```

**Ожидаем:** публикация успешна, карточка доступна, но новое объявление пока не появилось в поиске. В outbox остаётся неотправленное событие; `pending` больше нуля. Проверка готовности сервиса по БД может оставаться успешной, хотя Kafka выключена.

5. Верните Kafka:

```sh
docker compose --env-file .local/.env start kafka
```

6. Повторите `SELECT` через некоторое время и обновите каталог. Ожидается `pending = 0` и появление объявления. Запуск контейнера не равен мгновенной готовности брокера: восстановление и следующая попытка отправки занимают время.

**Где читать:** [платформенный запуск и outbox worker](../../internal/platform/app/run.go), [отправка в Kafka](../../internal/platform/kafka/transport.go).

**Проверочный вопрос:** почему нельзя бесконечно держать Kafka выключенной? Outbox продолжает расти в PostgreSQL; ресурсы базы ограничены. Если база больше не может сохранить транзакцию, успешной публикации уже не будет.

**Если публикация сразу вернула ошибку:** проверьте версию объявления, заполнение обязательных полей и готовность фотографии. Это отдельные проверки Listings, которые не исчезают при отказе Kafka.

## 3. Search выключен и затем догоняет журнал

**Что изучаем:** запись объявлений и выдача каталога обслуживаются разными сервисами.

```sh
docker compose --env-file .local/.env stop search
```

Пока Search остановлен, измените цену или описание своего опубликованного объявления под Анной. Попробуйте открыть каталог Бориса.

**Ожидаем:** операции Listings продолжаются, а каталог отвечает ошибкой. Остановленный Search не обслуживает даже старую выдачу. Kafka при этом продолжает принимать события, и группа Search отстаёт.

Верните Search:

```sh
docker compose --env-file .local/.env start search
```

Посмотрите lag:

```sh
docker compose --env-file .local/.env exec -T kafka \
  /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka:9092 --all-groups --describe
```

**Ожидаем:** каталог снова открывается, затем показывает новое состояние; отставание **активной** группы Search уменьшается. Если ранее запускали reindex, активная группа может называться `search-reindex-<UUID>`, а не `search-v1`. Как найти её — в [runbook событий](../runbooks/events.md).

После завершения ручного упражнения можно отдельно запустить автоматическую проверку:

```sh
make test-resilience
```

Она снова намеренно остановит Search и Kafka, проверит публикацию при отказе, вернёт сервисы и дождётся объявления в поиске. Код: [recovery_test.go](../../tests/resilience/recovery_test.go). При аварийном завершении тестового процесса выполните команду `start kafka search` вручную.

**Граница проверки:** тест подтверждает восстановление этого сценария с сохранёнными данными. Он не уничтожает узел или том Kafka, не проверяет несколько брокеров и не доказывает сохранение всей истории после потери диска. Хотя в имени теста упоминается опустошение outbox, итоговое утверждение проверяет появление нужного объявления в Search, а не SQL-счётчик всей очереди.

## 4. Одно событие пришло дважды или пришла старая версия

**Что изучаем:** повтор записи допустим, но повтор не должен ломать состояние.

Откройте [outbox_test.go](../../tests/integration/outbox_test.go) и [search_test.go](../../tests/integration/search_test.go). Первый моделирует «Kafka приняла событие, отметка отправки в БД не записалась». Второй применяет опубликованную версию 3, затем снятую версию 4, затем старую опубликованную версию 3.

Из корня выполните:

```sh
make test-integration
```

**Ожидаем:** тесты завершаются с `PASS`. Для SQL используются отдельные временные схемы в существующих базах; тестам также нужны реальные Kafka/S3. Не прерывайте тесты без необходимости: обычная очистка выполняется при завершении теста.

Ответьте по коду:

- Почему повторная публикация outbox сохраняет прежний `event_id`?
- Какое SQL-условие не даёт версии 3 заменить версию 4?
- Почему подтверждение Kafka `acks=all` не делает PostgreSQL и Kafka одной транзакцией? В локальном стенде реплика Kafka вообще одна.
- Что можно потерять, если сохранить offset до фиксации результата в базе обработчика?

Проверка «старый `published` после нового `withdrawn` не возвращает товар в поиск» **уже есть** в `search_test.go`; найдите её финальное утверждение. Не нужно менять рабочие события вручную, чтобы увидеть этот случай.

## 5. Браузер повторил отправку сообщения

**Что изучаем:** `Idempotency-Key` позволяет отличить повтор того же запроса от нового намеренного сообщения.

1. Под Борисом начните переписку по объявлению Анны и отправьте сообщение.
2. Откройте инструменты разработчика браузера → Network. Найдите POST отправки сообщения и заголовок `Idempotency-Key`.
3. Через действие браузера «Copy as fetch» скопируйте **свой** запрос. Повторите его в консоли того же браузера с тем же телом и ключом.
4. Затем повторите с изменённым текстом и тем же ключом. После этого попробуйте новый ключ.

**Ожидаем:** первый повтор возвращает то же сообщение с тем же ID; в переписке не появляется вторая строка. Другое тело при старом ключе даёт конфликт `409`. Новый ключ означает новое намеренное сообщение и может создать ещё одну строку, даже если текст похож.

**Где читать:** [Messaging handler](../../services/messaging/handler.go), [миграция](../../services/messaging/migrations/000001_messaging.up.sql), [интеграционные тесты](../../tests/integration/messaging_test.go).

Скопированный запрос содержит ваши cookies/токен. Не отправляйте его другим людям и не вставляйте в консоль чужой код. Если получили `401`, сессия могла истечь: сначала войдите заново и скопируйте новый собственный запрос. Это не опровергает работу ключа идемпотентности.

## 6. SMTP выключен, письмо ждёт следующей попытки

**Что изучаем:** запись сообщения и отправка email — разные этапы. Email может задержаться, хотя переписка уже сохранена.

Остановите Mailpit, который здесь играет роль SMTP-сервера:

```sh
docker compose --env-file .local/.env stop mailpit
```

Отправьте новое сообщение Бориса Анне. Через небольшой промежуток посмотрите задания:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U notifications -d notifications \
  -c 'SELECT id, state, attempts, next_attempt, last_error FROM jobs ORDER BY created_at DESC LIMIT 10;'
```

**Ожидаем:** сообщение видно в переписке; у нового задания растёт `attempts`, состояние после неудачной попытки — `pending`, а `next_attempt` показывает время следующей. В момент обработки можно увидеть `processing`. `last_error` показывает категорию ошибки, не адрес получателя.

Верните Mailpit:

```sh
docker compose --env-file .local/.env start mailpit
```

Дождитесь `next_attempt` и откройте [Mailpit](http://127.0.0.1:8025). Повторные попытки имеют паузы 10 секунд, 1 минуту, 5 минут и 30 минут; мгновенного письма после `start` может не быть. После успеха ожидается `sent`. Если достигнуто `failed`, автоматические попытки прекращены; восстановите только выбранное задание по [инструкции](../runbooks/events.md).

**Где читать:** [worker.go](../../services/notifications/worker.go) и [inbox.go](../../services/notifications/inbox.go). Worker арендует задание на 60 секунд; это позволяет подобрать его после падения. Найдите условие `lease_owner` при сохранении результата.

**Проверочный вопрос:** что будет, если SMTP принял письмо, а процесс умер до записи `sent`? Возможен повтор письма. Inbox защищает создание задания от повтора Kafka-события, но не делает SMTP и PostgreSQL общей транзакцией.

## 7. Построить поиск заново без удаления текущей выдачи

**Что изучаем:** поисковую копию можно восстановить из данных Listings и новых событий.

Посмотрите активную проекцию:

```sh
docker compose --env-file .local/.env exec -T postgres psql -U search -d search \
  -c 'SELECT p.id,p.group_id,p.ready FROM projections p JOIN settings s ON s.active_projection=p.id;'
```

Запомните ID. Запустите:

```sh
docker compose --env-file .local/.env --profile tools run --rm --build reindex
```

Пока идёт построение, если успеваете, измените цену учебного объявления и снимите другое с продажи. На маленьком наборе данных reindex может завершиться быстрее ручных действий; это нормально.

**Ожидаем:** сообщение `Active projection:` с новым UUID; после повторного SQL-запроса видны этот ID, новая группа и `ready = t`. Каталог показывает актуальные опубликованные объявления и не возвращает снятые. В процессе создания HTTP-поиск читает старую проекцию.

**Где читать:** [reindex.go](../../services/search/reindex.go), [worker.go](../../services/search/worker.go), [тесты reindex](../../tests/integration/reindex_test.go). Найдите начальную границу Kafka, постраничный экспорт, проверку догоняющей обработки и транзакцию переключения.

**Если перестроение не удалось:** старая активная проекция должна сохраниться. Разберите ошибку по [runbook](../runbooks/events.md), устраните причину и повторите команду с новым автоматически созданным UUID. Не правьте `settings.active_projection` вручную и не удаляйте рабочую проекцию ради симуляции сбоя.

## 8. Два редактирования и чужой доступ

**Что изучаем:** токен подтверждает пользователя, а сервис отдельно проверяет, что этому пользователю разрешена операция.

1. Под Анной откройте редактор одного объявления в двух вкладках. Обе вкладки сначала должны получить одну и ту же версию.
2. Измените и сохраните объявление в первой вкладке.
3. Не обновляя вторую, измените другое поле и сохраните.

**Ожидаем:** вторая операция получает конфликт, а первая не теряется. Обновите карточку, прочитайте новое состояние и внесите изменение заново. Старая `expected_version` — основание отказать, а не молча затереть данные.

Под Борисом попробуйте повторить запрос изменения объявления Анны с собственным токеном. Для проверки доступа к переписке нужен диалог, в котором текущий пользователь **не участвует**: Борис имеет право читать свой диалог с Анной. Создайте третью учебную учётную запись или изучите готовую проверку в тестах.

**Ожидаем:** чужое изменение и чтение чужой переписки не выполняются. Интерфейс может вообще не показать чужую кнопку, но проверка должна быть и на сервере. Не подменяйте токен на токен владельца: тогда вы проверите уже другой сценарий.

**Где читать:** [Listings handler](../../services/listings/handler.go), [Messaging handler](../../services/messaging/handler.go), [тесты Listings](../../tests/integration/listings_test.go) и [Messaging](../../tests/integration/messaging_test.go). Сверьте точный HTTP-код с тестом выбранного маршрута; отказ не всегда обязан раскрывать, существует ли чужой объект.

## 9. Спланировать собственное изменение

Это отдельное упражнение по разработке; выполнять его кодом для прохождения предыдущих упражнений не требуется. Пример: добавить фильтр по состоянию товара — «новый» или «б/у».

Сначала запишите простыми словами:

1. Кто задаёт значение, обязательно ли оно и что значит отсутствие у старых объявлений?
2. Где исходное поле хранится: в Listings. Как оно попадёт в событие и экспорт для переиндексации?
3. Как Search сохранит поле и применит фильтр? Как интерфейс передаст параметр?
4. Как новый обработчик прочитает старое событие без поля? Что произойдёт, пока старая и новая версии сервисов работают одновременно?
5. Какие проверки подтвердят создание, изменение, поиск, старые данные и восстановление через reindex?

Затем проследите цепочку файлов: миграция Listings → входные данные/проверки → snapshot/schema → Search → фильтр API → интерфейс → тесты → документация. Не начинайте с удаления старого поля или переписывания уже применённой миграции. Сначала расширяйте контракт совместимым способом, а удаление старого оставляйте на отдельное обновление.

После любого упражнения верните остановленные контейнеры и проверьте пользовательский сценарий. Полный сброс данных не является обязательной частью этих занятий.
