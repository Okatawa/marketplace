# Упражнения: читать код через наблюдаемые эффекты

Выполняйте упражнения на локальном стенде. Перед началом — `make up`, `make seed`; для метрик — `make observability-up`. Используйте отдельные объявления и не запускайте тесты параллельно с ручной остановкой зависимостей.

## 1. Одно изменение — две модели данных

Откройте редактор объявления Анны и каталог под Борисом. Измените цену, сохраните и обновите каталог.

Проследите запрос через `services/listings/handler.go`, outbox и `services/search/projection.go`. Владелец получает актуальную карточку из Listings, каталог — из Search. Найдите, где появляется новая `version` и почему Search может кратковременно показывать старую цену.

Затем снимите объявление с продажи. Оно исчезает из поиска, но карточка сохраняет статус, а существующий диалог продолжает работать. Найдите, зачем проекция сохраняет версию снятого объявления вместо физического удаления строки.

## 2. Kafka недоступна, публикация сохраняется

Создайте черновик с фотографией, затем остановите брокер:

```sh
docker compose --env-file .local/.env stop kafka
```

Опубликуйте черновик. Ожидаемое поведение: сохранение успешно, карточка доступна владельцу, поиск пока не обновился. Проверьте pending/age outbox Listings. Readiness по БД остаётся успешной.

Верните брокер:

```sh
docker compose --env-file .local/.env start kafka
```

Дождитесь появления объявления в поиске и уменьшения backlog. Объясните, почему API не должен был откатывать успешную транзакцию из-за недоступной Kafka, и что произойдёт при исчерпании диска БД.

## 3. Search догоняет накопленную историю

```sh
docker compose --env-file .local/.env stop search
```

Создайте или измените несколько объявлений. Каталог при остановленном Search отвечает ошибкой upstream, а операции Listings продолжаются.

```sh
docker compose --env-file .local/.env start search
```

Проследите lag и обновление выдачи. Затем запустите `make test-resilience`: он автоматизирует остановку Kafka/Search, публикацию и восстановление. Найдите в тесте, какие утверждения действительно проверяют восстановление, а какие свойства, например отказ узла Kafka, остаются за его пределами.

## 4. Дубликат события и старая версия

Прочитайте тесты `tests/integration/outbox_test.go` и `tests/integration/search_test.go`. Первый создаёт ситуацию «Kafka приняла событие, но отметка в БД не записалась». Второй проверяет выбор новой версии.

```sh
make test-integration
```

Ответьте по коду:

- Почему два экземпляра одного события имеют одинаковый `event_id`?
- Какое условие SQL не даёт версии 2 заменить версию 3?
- Почему `acks=all` и идемпотентный producer не дают атомарность PostgreSQL + Kafka?
- Что случилось бы, если consumer коммитил offset до транзакции своей БД?

Расширение упражнения: добавьте проверку старого `published` после нового `withdrawn`, чтобы снятое объявление не воскресало в поиске.

## 5. Повторная отправка сообщения

Создайте диалог Бориса с Анной. В DevTools Network найдите POST сообщения и его `Idempotency-Key`. Повторите запрос с тем же ключом и телом через встроенное «Copy as fetch» в своём браузере.

Ожидаемое поведение: тот же ID сообщения, одна запись переписки. Измените тело, сохранив ключ: должен получиться конфликт. Передайте новый ключ: это уже новое намеренное сообщение.

Сверьте поведение с `services/messaging/handler.go` и миграцией Messaging. Не публикуйте скопированные запросы с Authorization/cookies.

## 6. Письмо ждёт SMTP

```sh
docker compose --env-file .local/.env stop mailpit
```

Отправьте сообщение. Переписка работает; у Notifications появляется задание с попытками и следующей датой отправки. Прочитайте `services/notifications/worker.go`: какие операции входят в аренду, как worker узнаёт, что всё ещё владеет заданием?

```sh
docker compose --env-file .local/.env start mailpit
```

Дождитесь очередной попытки и письма в Mailpit. Если задание уже стало `failed`, оно автоматически не оживает; разберите его по [runbook событий](../runbooks/events.md).

Объясните окно сбоя между успешной отправкой SMTP и записью `state='sent'`. Почему уникальный inbox не может закрыть это окно? Какие гарантии мог бы дать внешний provider с идемпотентным ключом отправки?

## 7. Восстановить поиск из источника истины

Запустите [reindex](../runbooks/events.md) и продолжайте менять объявления во время импорта. Сравните активную проекцию до и после. Проверьте актуальную цену и отсутствие снятых объявлений.

Найдите в `services/search/reindex.go` начальную границу Kafka, экспорт снимка, проверку catch-up и транзакцию переключения. Объясните, зачем учитывать новые события ещё во время чтения снимка и что произойдёт, если retention удалит необходимую историю.

Не удаляйте рабочую проекцию, чтобы симулировать «восстановление»: отдельная новая проекция уже позволяет изучить этот процесс без разрушения текущей выдачи.

## 8. Доступ и конфликт редактирования

Откройте редактор одного объявления в двух вкладках Анны. Сохраните изменение в первой, затем другое во второй со старой версией. Вторая операция должна получить конфликт, а не затереть новое состояние.

Под Борисом попробуйте изменить объявление Анны и прочитать чужой диалог. Проверьте отказ в целевом сервисе, затем найдите соответствующий integration test. Gateway проверяет токен, но не заменяет проверку владельца/участника.

## 9. Подготовить собственное изменение

Добавьте, например, фильтр по состоянию товара. Сначала определите владельца поля и ограничения API. Затем проследите изменение по цепочке: миграция Listings → input/validation → snapshot/schema → Search → фильтр API → UI → тесты → документация.

Отдельно решите, как старые события без поля будут обрабатываться новым Search и что увидит старая версия приложения во время rollout. Это упражнение на совместимость контрактов и expand/contract, а не только на добавление колонки.
