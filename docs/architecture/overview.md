# Архитектура и границы гарантий

## От пользовательского действия к данным

Gateway публикует только явный список API-маршрутов. Accounts управляет личностью, Listings — объявлениями и фотографиями, Messaging — приватной перепиской. Search хранит копию публичных данных для чтения. Notifications превращает события о сообщениях в задания отправки писем.

У пяти сервисов есть собственные базы и роли PostgreSQL. Локально они находятся на одном сервере. Нет общих бизнес-таблиц, SQL JOIN между сервисами и распределённой транзакции. HTTP используется там, где результат нужен сейчас: например, Messaging проверяет статус объявления при открытии диалога. Kafka передаёт изменения, которые другие сервисы могут обработать позже.

Общий `internal/platform` содержит технические механизмы. Бизнес-правила находятся в `services/<name>`, wiring — в `cmd/<name>`. Один Go module позволяет менять учебный пример без публикации внутренних библиотек. По мере роста команды можно выделять модули; сами границы данных от этого не меняются.

## Почему Kafka

Для этого проекта полезны долговечный журнал, независимые consumer groups и возможность повторно прочитать изменения. Search и Notifications управляют своими offsets. Kafka не делает запись в PostgreSQL и отправку письма одной транзакцией — эту границу нужно обрабатывать в приложении.

| Поток | Ключ партиционирования | Обычная группа |
|---|---|---|
| `marketplace.listings.v1` | ID объявления | `search-v1` до первой переиндексации |
| `marketplace.messages.v1` | ID диалога | `notifications-v1` |

Локально у топиков три партиции, replication factor 1 и retention семь дней. Порядок существует внутри партиции. Увеличение числа партиций может переназначить ключи; это изменение требует отдельного плана миграции, а не случайного редактирования значения.

Producer использует подтверждение всех текущих ISR. При единственной реплике это всё равно один узел. Для внешнего кластера обычно рассматривают replication factor 3 и `min.insync.replicas=2`, но выбор нужно связать с доступностью, ресурсами и допустимой потерей данных. Поддержаны TLS и SASL/PLAIN через переменные окружения; локальная сеть Compose использует plaintext.

## Outbox: что происходит при публикации

```mermaid
sequenceDiagram
    participant U as Владелец
    participant L as Listings
    participant DB as БД Listings
    participant P as Publisher
    participant K as Kafka
    participant S as Search
    U->>L: publish(expected_version)
    L->>DB: BEGIN; lock; listing + version + outbox; COMMIT
    L-->>U: актуальная карточка
    P->>DB: следующая неотправленная запись
    P->>K: snapshot, key=listing_id
    K-->>P: подтверждение
    P->>DB: sent_at = now()
    K->>S: snapshot
    S->>S: применить, только если версия новее
    S->>K: commit offset
```

Изменение объявления и запись outbox коммитятся вместе. Если Kafka недоступна, объявление сохраняется, а outbox растёт. Один активный publisher выбирается PostgreSQL advisory lock; он не обгоняет запись, отправка которой завершилась ошибкой.

Если процесс падает после подтверждения Kafka, но до `sent_at`, событие отправится повторно. Идемпотентность Kafka producer не устраняет этот разрыв между двумя системами. Поэтому доставка — **at least once**.

Search делает условный UPSERT по версии объявления. Повторная или более старая версия ничего не меняет. Снятое объявление остаётся в проекции с новой версией и статусом `withdrawn`: иначе старое событие могло бы вернуть его в выдачу.

## Переписка, inbox и SMTP

Открытие диалога идемпотентно для объявления, покупателя и продавца. Читать и писать могут только участники. Для нового сообщения клиент передаёт `Idempotency-Key`: повтор с тем же телом возвращает прежний результат, а с другим телом получает конфликт. Запись сообщения и outbox атомарны.

Событие содержит идентификаторы сообщения, диалога, отправителя и адресата. Текста переписки и email в нём нет. Notifications одной транзакцией сохраняет уникальный `event_id` в inbox и создаёт задание. Затем worker получает email по внутреннему API Accounts.

Задание арендуется на 60 секунд с идентификатором worker-а. Используется `FOR UPDATE SKIP LOCKED`, чтобы несколько экземпляров не взяли одну работу одновременно. После временной ошибки предусмотрены задержки 10 секунд, 1 минута, 5 минут и 30 минут; после пяти попыток — `failed`. Истёкшая аренда позволяет продолжить работу после падения.

SMTP — внешний эффект. Падение после успешной отправки и до обновления `jobs` может породить второе письмо. Inbox защищает от повторного создания задания, но не обещает exactly-once отправку. Письмо содержит ссылку на диалог, а не текст сообщения.

## Ошибки событий и полная переиндексация

Consumer коммитит offset после успешной обработки. Временные ошибки повторяются с задержкой до 30 секунд. Некорректная оболочка или payload отправляются в `<source-topic>.<group>.dlq`; исходный offset продвигается после подтверждения DLQ. Дубликаты DLQ возможны и определяются исходными topic/partition/offset.

История Kafka ограничена retention. Для полного восстановления Search нужен актуальный экспорт Listings, а не только чтение оставшихся событий. Команда reindex создаёт новую проекцию и группу, фиксирует начальные offsets, запускает обработку изменений и импортирует снимок по стабильному ID. Более новые версии побеждают независимо от порядка прихода.

После импорта команда дожидается контрольной границы Kafka и проверяет доступность необходимой истории. Только после этого новая проекция становится активной. Обычный worker Search обнаруживает переключение. При неуспехе остаётся старая проекция. Это одна команда с автоматической активацией после проверки; отдельного ручного шага `activate` нет.

## Безопасность и наблюдаемость

Пароли хешируются bcrypt. Access token Ed25519 действует 15 минут; сервер хранит хеш refresh token, а браузер — HttpOnly cookie. Обновление сессии одноразово ротирует refresh token. Origin и SameSite защищают операции с cookie. Logout отзывает refresh-сессию; выданный access token продолжает действовать до истечения срока.

Gateway удаляет поддельные заголовки идентичности. JWT проверяют Gateway и сервисы, права проверяет владелец данных. Внутренние HTTP-маршруты не включены в публичный allowlist.

Фото JPEG/PNG проходят декодирование и ограничения размера: до 5 МиБ, 20 миллионов пикселей, восьми фото на объявление. S3 bucket приватный; Listings выдаёт временные ссылки после проверки доступа. Фоновая очистка обрабатывает незавершённые загрузки и удаления.

`log/slog` пишет JSON в stdout. HTTP-логи содержат технические поля запроса, но не Authorization, тело сообщения или аргументы SQL. OpenTelemetry создаёт spans HTTP, SQL и Kafka, переносит trace context в заголовках HTTP/Kafka и через outbox. Collector отправляет traces в Jaeger. Prometheus собирает HTTP-метрики, размер и возраст outbox, lag групп и состояния email-заданий; Grafana показывает начальные панели.

Liveness показывает, что HTTP-процесс отвечает. Readiness проверяет БД у сервисов с хранилищем; Gateway не делает каскадную проверку upstream. Readiness не гарантирует свежесть Search или работоспособность SMTP. Для этих свойств нужны lag, возраст outbox и состояние заданий. Это сознательно простая текущая реализация, которую можно усилить под конкретный SLO.

## Что нужно до публичной эксплуатации

- Отдельные сервисные credentials и минимальные Kafka/S3/DB права вместо общего `SERVICE_TOKEN`; управляемая ротация JWT с несколькими ключами.
- HTTPS, SMTP с TLS, секреты из менеджера секретов, сетевые политики с поддерживающим их CNI и проверка цепочки доверенных proxy.
- Rate limit на уровне всей системы. Сейчас лимит каждого Gateway основан на адресе соединения; за ingress пользователи могут делить адрес proxy и общий лимит.
- Подтверждение email, восстановление доступа, модерация, жалобы, защита от спама, квоты файлов и правила хранения/удаления персональных данных.
- Репликация зависимостей, резервные копии с проверкой восстановления, нагрузочные тесты, SLO и настроенные получатели оповещений.
- План очистки отправленного outbox, старого inbox, завершённых jobs и неактивных поисковых проекций. Автоматическая политика хранения этих таблиц пока не реализована.
