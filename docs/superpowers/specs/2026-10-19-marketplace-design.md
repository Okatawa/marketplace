# Учебный маркетплейс на Go

Статус: согласовано пользователем 2026-10-19, включая описанные в чате пользовательские сценарии. Брокер событий — Kafka.

## Цель и критерий успеха

Создать небольшой аналог Авито, на котором можно изучать устройство большого Go-приложения: границы микросервисов, владение данными, обмен событиями, обработку сбоев, тестирование и развёртывание. Пользователь должен иметь возможность читать код, менять отдельный сервис и наблюдать последствия в работающей системе.

Результат — рабочий монорепозиторий, а не набор заглушек. Локальный стенд запускается документированной командой, заполняется демоданными и позволяет выполнить сценарий: регистрация → публикация объявления с фотографией → поиск другим пользователем → сообщение продавцу → email в локальном тестовом почтовом ящике.

Проект показывает эксплуатационные практики, но не заявляет готовность обслуживать реальных пользователей без настройки инфраструктуры, безопасности, резервного копирования и нагрузочной проверки.

## Границы первой версии

Включены аккаунты, объявления, категории, поиск по тексту и фильтрам, фотографии, личная переписка и email-уведомления. Минимальный веб-интерфейс нужен для проверки сценария; основная учебная ценность находится в Go-сервисах и инфраструктуре.

Переписка использует HTTP и периодическое обновление списка сообщений. Платежи, доставка, рекомендации, геопоиск, автоматическая модерация и WebSocket не входят в первую версию.

### Согласованные пользовательские сценарии

- Гость просматривает опубликованные объявления и их карточки, ищет по тексту, категории и диапазону цен; для публикации и переписки требуется вход.
- Пользователь регистрируется по имени, email и паролю, входит, изменяет отображаемое имя и выходит. Email не включается в публичный профиль.
- Владелец создаёт черновик с названием, описанием, категорией, ценой и фотографиями, сохраняет его, публикует, редактирует, снимает с продажи и публикует повторно. Черновик виден только владельцу. Снятое объявление отсутствует в поиске; его карточка показывает статус, а существующие переписки сохраняются.
- Покупатель открывает диалог из карточки объявления. Повторное открытие возвращает тот же диалог для пары покупатель/продавец по этому объявлению. Список диалогов показывает объявление, собеседника и последнее сообщение. Читать и отправлять сообщения могут только участники.
- Email уведомляет о новом сообщении и содержит ссылку на диалог. В локальном стенде письма доступны в веб-интерфейсе тестового почтового сервера.
- Веб-интерфейс включает каталог, карточку, регистрацию/вход, профиль, мои объявления, редактор и переписки. Он показывает ошибки полей и пустую выдачу, сохраняет введённый текст формы при неуспешном запросе и автоматически обновляет открытую переписку раз в несколько секунд.
- После сохранения владелец сразу видит актуальное объявление; интерфейс объясняет возможную задержку появления изменений в поиске.

Избранное, отзывы, подписки на поиск, платное продвижение и интерфейс модератора не входят в первую версию. Сама сделка происходит вне приложения.

## Компоненты и данные

| Компонент | Ответственность | Собственные данные |
|---|---|---|
| Gateway | Публичный HTTP API, маршрутизация, request ID, ограничения запросов | Постоянного хранилища нет |
| Accounts | Регистрация, вход, обновление и отзыв сессий, публичный профиль | Пользователи, хеши паролей, сессии |
| Listings | Создание, изменение, публикация и снятие объявлений, категории, фотографии | Объявления, метаданные файлов, outbox |
| Search | Текстовый поиск, фильтры по категории и цене, пагинация | Поисковая проекция, версии объявлений |
| Messaging | Диалоги по объявлениям и сообщения участников | Диалоги, сообщения, ключи идемпотентности, outbox |
| Notifications | Обработка событий о сообщениях и отправка email | Входящие события, задания отправки, попытки и результат |

Каждый сервис с постоянными данными владеет отдельной базой PostgreSQL и ролью. Локально базы могут размещаться в одном экземпляре PostgreSQL. Межсервисные SQL-запросы, общие таблицы и внешние ключи между базами запрещены. Search использует полнотекстовый поиск PostgreSQL.

Файлы хранятся в S3-совместимом хранилище; локальный стенд включает совместимую реализацию. Listings принимает загрузку с ограничением размера, проверяет тип изображения и права пользователя, затем связывает объект с объявлением. Очистка несвязанных объектов выполняется отдельной фоновой задачей.

Исходники сервисов находятся в отдельных каталогах, имеют самостоятельные точки входа и образы. В первой версии используется один Go module. Общие библиотеки ограничены техническими задачами: конфигурация, HTTP, телеметрия и оболочка события. Бизнес-модели принадлежат сервисам.

## Синхронные контракты и безопасность

Внешние и внутренние запросы используют HTTP/JSON. OpenAPI описывает маршруты, ошибки, авторизацию и пагинацию. Ошибки имеют стабильный код, понятное сообщение и request ID; внутренние детали не раскрываются клиенту.

Accounts выдаёт короткоживущий подписанный access token и обновляемую сессию. Пароли хешируются специализированной библиотекой; refresh token хранится на сервере только в виде хеша и ротируется при использовании. Выход отзывает сессию; уже выданный access token действует до истечения короткого срока. Браузер хранит refresh token в HttpOnly cookie; операции с cookie защищены проверкой Origin и настройками SameSite. Производственное окружение требует HTTPS.

Gateway и целевые сервисы проверяют access token; права на объявления и диалоги проверяются в сервисе-владельце данных. Произвольным заголовкам с идентификатором пользователя доверять нельзя. Внутренние служебные API требуют отдельной сервисной аутентификации и закрыты от публичного ingress. Notifications получает email адресата через ограниченный внутренний API Accounts; email и токены не попадают в события и логи.

На входе задаются лимиты тела, пагинации и длительности запросов. Ограничение частоты запросов в учебном Gateway действует на экземпляр; это ограничение явно описывается для развёртывания с несколькими репликами.

## Kafka и события

Kafka работает в режиме KRaft. Локально используется один брокер с постоянным томом. Такая конфигурация позволяет изучать перезапуски, но не отказоустойчивость к потере узла. Для внешнего кластера отдельно документируются репликация, минимальное число синхронных реплик, TLS и учётные данные.

Основные топики:

| Топик | Ключ | Содержимое | Потребитель |
|---|---|---|---|
| `marketplace.listings.v1` | `listing_id` | Версия и публичный снимок объявления, включая статус | Группа `search-v1` |
| `marketplace.messages.v1` | `conversation_id` | ID сообщения, диалога, отправителя и адресата; без текста сообщения | Группа `notifications-v1` |

Оболочка события содержит `event_id`, `event_type`, `schema_version`, `occurred_at`, `aggregate_id`, `aggregate_version` и `payload`. Контекст трассировки передаётся в заголовках Kafka. Формат — JSON с документированными схемами. Совместимые расширения добавляют необязательные поля; несовместимые изменения требуют новой версии контракта.

Сервис сохраняет бизнес-изменение и outbox одной транзакцией PostgreSQL. Фоновый publisher отправляет событие с подтверждением брокера и затем помечает запись отправленной. Сбой между этими действиями приводит к повторной публикации: обработчики обязаны переносить дубликаты. В первой версии один активный publisher на сервис выбирается блокировкой PostgreSQL; он публикует последовательность outbox без обгона предыдущей записи при ошибке. Версия агрегата назначается под блокировкой его записи в бизнес-транзакции.

Для классических consumer groups порядок сохраняется внутри партиции. Число партиций фиксируется в локальной конфигурации; его изменение требует отдельной процедуры, поскольку ключ может попасть в другую партицию. Обработчик работает последовательно внутри партиции и фиксирует offset только после успешной транзакции в своей базе. При ошибке фиксации offset возможна повторная обработка.

Search применяет снимок только при более новой версии объявления. Снятие с продажи убирает объявление из выдачи, но сохраняет его версию, чтобы запоздалое событие не вернуло старые данные. Notifications сохраняет входящее событие и задание отправки одной транзакцией с уникальным `event_id`.

Временные ошибки инфраструктуры вызывают ограниченные по частоте повторные попытки с задержкой и сигналом о задержке обработки; события не пропускаются. Некорректное событие после проверки направляется в отдельный топик ошибок соответствующего сервиса. Offset исходного сообщения продвигается только после подтверждения записи в топик ошибок. Повторная запись ошибки допустима; её идентичность определяется исходными topic/partition/offset. Есть инструкция просмотра и ручного повторного запуска после исправления причины.

Email отправляет отдельный worker из таблицы заданий Notifications. Используются повторные попытки, предел попыток и состояние окончательной ошибки. SMTP не предоставляет общей транзакции с PostgreSQL: при сбое после отправки письма до сохранения результата возможен дубликат. Проект явно демонстрирует это ограничение и не обещает exactly-once для внешних эффектов.

Локальный срок хранения событий — семь дней. Повторное чтение предназначено для восстановления обработки в пределах сохранённой истории. Полное восстановление Search поддерживается экспортом текущих объявлений и их версий из Listings: сначала новая группа начинает сохранять/обрабатывать изменения, затем загружается постраничный снимок по стабильному ID; версии защищают от устаревших записей. Снятые объявления сохраняются как записи со статусом. Физическое удаление объявлений не входит в первую версию. Процедура контролирует lag и не должна пережить истечение доступной истории.

## Наблюдаемость и жизненный цикл

Логи — JSON через `log/slog` в stdout, с service name, request ID и trace ID, без секретов и содержимого переписки. OpenTelemetry отвечает за трассировку HTTP, SQL и обработки событий. В стенде Collector принимает трассировки и передаёт их в Jaeger.

Prometheus собирает метрики HTTP, ошибок, времени обработки, размера и возраста outbox, consumer lag и заданий уведомлений. Grafana содержит начальные панели и примеры сигналов об ошибках. Расширенный набор наблюдаемости запускается отдельным профилем Compose.

У каждого процесса есть liveness и readiness. Readiness отражает возможность выполнять свою роль: например, отказ Kafka не запрещает Listings сохранять объявления с outbox, пока база доступна. Растущий outbox виден по метрикам. При завершении процесс прекращает принимать работу, завершает текущие операции в пределах таймаута и закрывает подключения.

## Запуск, развёртывание и CI

- Docker Compose: сервисы, PostgreSQL, Kafka, S3-совместимое хранилище, тестовый SMTP и демоданные; наблюдаемость подключается профилем.
- Многостадийные Dockerfile: отдельные образы сервисов, непривилегированный пользователь, фиксируемые версии зависимостей и базовых образов.
- Helm chart приложения: Deployments, Services, ingress, probes, requests/limits, ссылки на Secrets и конфигурация внешних зависимостей. Секреты не включаются в репозиторий.
- Миграции выполняются отдельным контролируемым шагом перед обновлением сервисов. CI проверяет миграцию пустой базы; несовместимые изменения требуют схемы expand/contract. Автоматический откат данных не обещается.
- Для проверки Kubernetes используется локальный кластер с явно описанной установкой зависимостей. Helm chart приложения не выдаётся за готовое отказоустойчивое развёртывание Kafka или PostgreSQL.
- GitHub Actions запускает форматирование, статический анализ, unit-тесты с race detector, интеграционные тесты, сборку образов и проверку Helm. Публикация образов и развёртывание требуют настройки реестра и окружения владельцем проекта.

## Проверка результата

1. Unit-тесты проверяют правила доступа, переходы статусов, валидацию и выбор более новой версии события.
2. Интеграционные тесты используют настоящие PostgreSQL и Kafka: миграции, outbox, дубликаты, фиксацию offset после обработки и обработку некорректного события.
3. Сквозной smoke-тест создаёт двух пользователей, публикует объявление, дожидается его появления в поиске, отправляет сообщение и проверяет письмо в тестовом SMTP.
4. Сценарии сбоев проверяют остановку Search, накопление событий и восстановление; недоступность Kafka и последующую отправку outbox; повторную доставку без двойного изменения данных.
5. Проверяются сборка образов, локальный запуск и рендер Helm. Реальное применение в Kubernetes отмечается как проверенное только после выполнения в доступном кластере.
